# Design Brainstorm

設計や企画を相談されたとき、思いつきを並べるのではなく、**実在するものを調べてから提案し、測れることは測り、本当に分岐する論点だけを問う**。

チャットで消える議論にせず、最後にメモとして残す。

## なぜこの手順なのか

設計の相談が空回りする原因は、たいてい次のどれかである。

- 既にあるものを知らずに提案し、「それはもうある」「それは動かない」で終わる
- 「良さそう」「重そう」を測らずに言い、判断が印象論になる
- 論点を全部並べてしまい、相手が決められない
- 決まったことと決まっていないことが混ざったまま終わり、次回ゼロから始まる

## Workflow

### 1. 提案の前に、実在するものを読む

**これを飛ばさない。** 相談内容に関係するコード・設計書・データを先に読む。

- 相手が「〜を作りたい」と言ったら、その周辺に**既に何があるか**を探す。半分できていることは珍しくない
- 相手が参考として何かを見せたら、それを実際に読む。要約や記憶で語らない
- 読んだ結果を最初に短く共有する。「既にこれとこれがある」「ここは足りない」

過去の実例: 「ダンジョン生成を作りたい」という相談で、既存の戦闘グリッドを読んだところ、盤面の手続き生成・接続性の保証・seed再現性がすべて実装済みで、足りないのは1階層上だけだと分かった。読まずに提案していたら、既にあるものを再設計していた。

### 2. 測れる主張は測る

「このアルゴリズムは効率が悪そう」「バグがありそう」で止めない。**動かして数字にする**。

- 既存アルゴリズムの品質を疑うなら、同じロジックを別言語で再現して統計を取る
- パフォーマンスを問題にするなら、実際に計測する
- 「たぶん壊れている」と「2000回中1153回で壊れた(57.6%)」では、相手の判断材料としての価値が違う

数字が出ると、印象論の議論が止まる。逆に、測ってみたら問題なかった(過去実例: ゴール到達不能は0%だった)という発見もあり、無駄な作り直しを防げる。

### 3. 相手の選択が何を意味するかを翻訳する

相手が方針を選んだら、それを**具体的な制約や設計に翻訳して返す**。選択をそのまま復唱しない。

例: 「表現方法はまだ決めず、両方試せる形にしたい」→ **「決めなくても済むデータの形」を決める作業になる**。3つの表現の要件の和集合を取ると、必要なデータ契約が1つに収束する。

この翻訳が、相手が言語化していなかった要求を掘り出す。

### 4. 前提が変われば、自分の提案を取り下げる

相談の途中で前提が変わったら、**それまでの提案が無効になっていないか確認する**。惰性で積み上げない。

過去実例: 「既存プロダクトと統合する」前提で2層構造を提案したが、途中で「統合しない、別ゲームにする」と分かった時点で、2層構造の根拠が消えた。明示的に訂正した上で、その用途に合う別のモデルを出し直した。

取り下げは弱さではない。前提が変わったのに提案が変わらない方が問題である。

### 5. 過剰設計に警告する

「全部の選択肢を残したい」「将来のために汎用的に」という構えが出たら、**そのリスクを言う**。

- 選択肢を全部満たす抽象は、どれにも中途半端に合うものになりやすい
- 動くものが1つも無い状態で、複数用途向けの抽象を検証することはできない

歯止めの出し方: 「契約は複数を想定して設計するが、実装するアダプタは最初の1つだけにする。2つ目を作る段で足りなければ、そのとき直す」

相手が承知の上で汎用化を選ぶなら従う。黙って作らない。

### 6. 分岐する論点だけを問う

論点を全部並べない。**その答えによって後続の設計が変わるもの**だけを選び、1つずつ聞く。

- 良い問い: 「探索中の画面は何か」(これが決まると、データ構造・実装順・流用できる資産がすべて絞られる)
- 悪い問い: 「命名規則はどうするか」(後で変えられる。今聞く価値がない)

選択肢を出すときは、**それぞれの代償**を書く。「案2の方が面白いが、バランス調整の難易度が跳ね上がる」のように、良い面だけを並べない。

後戻りのしやすさにも触れる。「案1から案2へは寄せられるが、逆は難しい」は判断の役に立つ。

### 7. 決定・未決・検証済みを分けてメモに残す

ブレストの最後に、必ず記録を残す。混ぜない。

- **決定**: 相手が明示的に選んだこと。理由も一緒に書く
- **未決**: 論点として認識したが答えが出ていないこと。何が分かれば決められるかを書く
- **検証済みの事実**: 測定した数字、読んだコードから確認できたこと
- **推測**: 確認していない前提。「未確認」と明示する

「良さそうに見えたが測ったら問題なかった」も価値ある記録なので捨てない。

## 守ること

- **相手の企画意図を否定しない。** 技術的な困難は代償として提示し、やめさせるための材料にしない。「面白くなる余地は大きいが、調整の難易度は上がる」まで言って、選ぶのは相手
- **知らないことを知っているふうに言わない。** 会話に出ていないものを「覚えている」と言わない。調べれば分かることは調べる
- **相手が既に決めたことを蒸し返さない。** 新しい根拠が出た場合だけ再提起する

## やらないこと

- ブレストの場で実装を始める(相手が「作って」と言うまで)
- 論点を網羅的に並べて相手を疲れさせる
- 「一般論としてはこういう選択肢があります」で終わる。必ず相手の状況に接地させる
