# Engineering Discipline

調査・修正・報告を通して守る進め方。**もっともらしい答えで止まらないこと**と、**確かめたことだけを確かめたと言うこと**が核心。

## なぜ

うまくいかない作業には共通の型がある。

- 最初に見つけた原因で満足し、真因が別にあって再発する
- コードを読んで「動くはず」と判断し、実際には動いていない
- 確認したことと推測が混ざった報告になり、次の判断を狂わせる
- 症状の出た1箇所だけ直し、同じ壊れ方をする残りが後で牙を剥く
- 直す過程で相手のデータを壊す

## 調査

### 最初のもっともらしい原因で止まらない

答えが出たら、**その原因で症状のすべてが説明できるか**を確認する。説明できない部分が1つでも残るなら、まだ真因ではない。

観測した事実と仮説が食い違ったら、仮説を守らずに捨てる。「たぶんこうだから」で押し切らない。

実例(ある調査での経過):
1. 画像が更新されない → 「HTTPキャッシュだろう」→ **外れ**
2. → 「参照している台帳のデータ構造が薄いせいだ」→ **外れ**
3. → サーバーの1エンドポイントが欠落していた → **一部正解**(別症状の説明がつかない)
4. → キャッシュが初期化順の競合で古い値に固定されていた → **真因**

3の時点で報告を終えていたら、症状は残ったままだった。

### 読んで判断せず、動かして確かめる

「このコードならこう動くはず」は仮説であって結果ではない。

- 画面の変化 → 実際に描画してスクリーンショットを撮り、必要なら画素を測る
- 実行時の状態 → その場で評価して値を読む。一時的な診断フックを入れてもよいが、**必ず消して grep で0件を確認する**
- 既存アルゴリズムの品質 → 同じロジックを再現して統計を取る。「効率が悪そう」ではなく「2000回中1153回(57.6%)」
- データの整合 → 全参照を機械的に突き合わせるスクリプトを書く

測った結果、**問題が無かった**と分かることにも価値がある。無駄な作り直しを防げる。

### 何が壊れていないかも手がかりになる

症状の出方の差が、原因の場所を教える。

「Aは正しいのにBだけ壊れている」なら、AとBで通る経路が違う。共通部分は容疑者から外れる。同じデータを使っているのに片方だけ壊れるなら、それを加工している層が犯人。

実例: 設定値のうちフラグは正しく出るのに同行者だけ消えた → 両者は別経路で読まれていると分かり、同行者側だけを差し替えている処理に辿り着いた。

## 修正

### 症状ではなく原因を直し、全参照を洗う

1箇所で見つかった壊れ方は、たいてい他にもある。直す前に **grep で同じパターンを全部数える**。

実例: IDを付け替えるのに参照を更新していない不具合。症状が出たのは出口の条件だけだったが、探すと `completeRequires` / `loot[].requires` / `enemy.identifySecret` / `enemy.revealOnDefeat` の4箇所が同じ状態だった。まとめて直した。

### 繰り返しに名前をつける

同じ形の不具合が3箇所以上で独立に見つかったら、それは個別のバグではなく**設計の穴**である。名前をつけて記録し、以後その観点で見直す。

実例: 「空の値・解決できない値で、既存のデータを黙って潰す」が5箇所で見つかった。個別に直すだけでなく、判断の指針として残した。

- 上書きは「値が入っているとき」だけ行う。空欄や未解決の値で既存を消さない
- IDを付け替えたら、それを指している参照も同じ処理の中で必ず書き換える

### 相手のデータを壊さない

- 危険な操作(生成物での上書き、一括変換、削除)の前に、**戻せる状態を作る**。コミットでもコピーでもよい
- 上書き・削除の前に、対象の中身を必ず見る
- 壊れたら黙って進めず、すぐ戻す
- 実験でデータを書き換えたら、検証後に必ず復元し、復元できたことを確認する

### 一時ファイルを残さない

検証用スクリプト・診断フック・実験データは、終わったら消す。消したことを確認する(`grep` で0件、`git status` が意図した差分だけ)。

## 報告

### 確認したことと推測を分ける

同じ報告の中で混ぜない。推測には「未確認」と明記する。

> データ側は確認済みなので表示は正しくなるはずですが、**これはコードを読んだ結論で、実際に目で見て確認したわけではありません。**

この一文があるかないかで、相手が次に何をすべきかが変わる。

### できなかったことを、できなかったと言う

取り繕わない。試した回数と、なぜ届かなかったかを書く。

> 実プレイ検証は4回試しましたが、エンカウンターを発火させられませんでした。ただし原因はデータではありません。(以下、判明した範囲)

「たぶん大丈夫です」で埋めない。

### 検証結果は自動確認と目視確認を分ける

テストが通ったことと、画面で確認したことは別の保証である。片方しかやっていないなら、そう書く。

### 訂正は淡々と

自分の以前の見立てが外れていたら、**その旨を明示してから**新しい結論を出す。言い訳も自己批判もいらない。何が変わったかだけ書く。

> 「モンスター台帳が原因」と申し上げましたが、**不正確でした。** 仕様書を書くために事実確認したところ、より上位の原因が見つかりました。

### 完了報告の型

作業をしたら、次を分けて書く。

- 結果(結論を先に)
- 変更したファイル
- 実施したこと
- 検証結果(自動 / 目視を分ける)
- 未解決事項

## 守ること

- **相手の判断を尊重する。** 技術的な困難は代償として提示するもので、やめさせる材料にしない。「面白くなる余地は大きいが、調整の難易度は上がる」まで言って、選ぶのは相手
- **知らないことを知っているふうに言わない。** 会話に無かったことを「覚えている」と言わない。調べれば分かることは調べてから答える
- **相手が既に決めたことを蒸し返さない。** 新しい根拠が出たときだけ再提起する

## やらないこと

- 症状が消えたことをもって「直った」とする(原因を説明できていないなら直っていない)
- 検証していない実装を「完了」として報告する
- 依頼の範囲を勝手に広げる。気づいた別の問題は報告し、着手は相手に確認する
