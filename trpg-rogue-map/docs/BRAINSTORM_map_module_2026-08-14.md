## 決定

### D1. ローグは地図の様式であって、ゲーム性ではない

作者の言葉: 「ローグにしたのは、MAPの方式をそんな感じにしたいだけで、ローグのゲーム性を移植したいからではありませんね」。

これで軸が変わる。面白さの中心はゲームブック（調査・段階的な発見・決断）であり、
地図は**位置関係を伝える器**、戦闘は**アクセント**である。潜る／引き返すのリソース管理は主役にしない。

**なぜ俯瞰なのか（作者の言葉・2026-08-14）:**
「シナリオ寄りで、俯瞰を重視しているのは、このゲーム性と差別化するためです。
**戦闘を繰り返すことを作業化しないためです**」。

ウィザードリィは一人称で移動し、地図は補助である。ここは逆にする。これは様式の好みではなく、
**戦闘の反復を主目的にしない**という設計判断であり、D1の理由そのもの。

| | 当初の前提 | 決定 |
|---|---|---|
| 霧 | 探索の緊張 | まだ見ていない場所がある、という表示 |
| 遭遇 | 消耗の管理 | 移動中に起きる出来事 |
| 地図 | ゲームの本体 | 位置関係を伝える器 |

### D2. 地図がハブ。戦闘と物語は呼ばれて返る

```
        ┌────────── 地図（移動が中心・ここが本体）──────────┐
        │                                                   │
   通路で遭遇 ──▶ isometric戦闘 ──結果──▶ 戻る             │
   目的地に到達 ──▶ ゲームブックのシーン ──結果──▶ 戻る    │
        └───────────────────────────────────────────────────┘
```

状態（HP・持ち物・進行）を持つのは地図側。2つのモジュールは預かって返す。
地図は呼ばれる側にならない。

### D3. 移動は本文の選択肢から外す。地図の上だけで行う

作者の提案:「曖昧な移動の選択肢を表示しない。基本移動は平面の4方向と、上下の2方向のみ」。

- `#choices` に残るのは調査・会話・戦闘・決断。移動は地図
- 本文の「奥へ進む」は**描写として残る**。ボタンでなくなるだけ
- テレポータ（縦坑・トロッコ・崩落した近道）は6方向の例外。格子に載らない接続の逃げ道にもなる

**これで既存3章はデータを1文字も直さずに載る。** `exits` の `match` 語が使われなくなるだけで、消す必要もない。

### D4. 相対方向（右・左）を使わない

「右」は入ってきた向きに依存するため、入口が2つある部屋で必ず壊れる（→ V3）。
絶対方向にすれば、この曖昧さは解けるのではなく**発生しない**。

副次的に、生成器の制約が1つ消える（→ V2）。作者は方向を書かなくてよくなる。

### D5. 生成器が守る制約は「方向」ではなく「入口からの遠さの順序」

`奥` が本文で28回と最多なのは方向ではなく**距離**の話。
灯りの部屋が入口の隣に生成されたら、方向が正しくても物語が壊れる。

生成器は部屋を発明しない。**章に書かれた部屋を置き、通路の長さと曲がりだけを乱数が決める。**
部屋数は作者が決め、NPCはその部屋に居る。

### D6. 遭遇は「通路を1本通る＝抽選1回」

作者の言葉:「既知の道でもたまにバトルしたいけどね」。

```
未踏の通路   高い確率（構想文書の「一度だけ」を保つ）
既知の通路   低い確率（たまに出る）
```

これ1つで次が同時に満たされる。調整する数字は確率1つだけで、
gamebookで `APPROACH_TURNS`/`APPROACH_MAX` の2つが当て推量のまま残った状態（§17.4）を繰り返さない。

- 既知の道でもたまに戦闘が起きる
- 近道に価値が出る。同行者の助言は「こっちが早い」ではなく「**こっちなら、あまり出くわさない**」
- 帰り道は既知なので低確率。帰還が罰にならない
- 手番・接近度を地図へ持ち込まなくてよい（基準点の問題が発生しない）

### D7. 地図は俯瞰、戦闘は詳細の地形

作者の言葉（この切り分けの正本）:「**地図は、俯瞰。戦闘は詳細の地形という切り分けです**」。

- 地図が答えるのは「**どこに何があるか**」
- 戦闘が答えるのは「**その場所がどうなっているか**」
- **迷ったら「これは俯瞰の情報か、詳細の情報か」で置き場が決まる。** 解像度の話ではなく、記述の水準の話

この一行があれば、V9の失敗（細部を地図へ持ち上げる／地図を戦闘の解像度へ合わせる）は起きない。


作者の言葉:「移動時は1マスでいいです。敵とエンカウントして、isometric戦闘になった時に3マス必要というだけです。
地図の構成は引き継ぎますが、戦闘の盤面にそのまま使うつもりはありません」。

作者の追加（同日）:「地図の見た目と、isometricのベースの地形は同じにしたい。
地図が右曲がりの通路ならば、戦闘の地形も右回り」「地図上で通路を3マスにする必要はない。1マスで良い。
部屋も地図上は矩形で良い」「通路もバトル側に接続していなくて良い」。

```
地図（区画解像度）   通路は1マス、部屋は矩形
   │ 形を渡す（種類／曲がりの向き／どの辺から入りどの辺へ出るか／部屋の縦横比）
   ▼
戦闘の盤面（拡大）   地図の形から【導出する】。データは共有しない
   ＋ 戦闘側だけが足す: えぐれ・遮蔽物・高さ・配置
```

- **えぐれは地図に出さない。** プレイヤーは戦闘に入って初めて「そこは行けない」と気づく
- **盤面は閉じている。** 通路へ繋げなくてよい。離脱は「逃げる」が成功したときだけ。
  これは既存の `junction.js`（9×7を壁で囲んだ箱）と同じ形で、複製する舞台の作りと一致する
- **形の一致＝データの共有ではない。** 導出なので解像度が違ってよい（→ V9 で実測した失敗）

### D8. シーンがある場所が部屋

作者の言葉:「基本、シーンがあるところは部屋になると思う」。
通路には部屋が無い＝物語も無い。通路で起きるのは遭遇だけ。

### D9. 見た目：塗りを基調。灯りが届く範囲だけが見え、外は霧

実際に描いて作者が確認済み（→ V5）。作者の評価:「私がイメージしていたものに近いです」。

- タイル画像は不要。**各マスで「繋がっている方向へ腕を伸ばす」だけ**で、16枚のタイルと同じ結果になる
- 有機的な坑道は `feTurbulence` + `feDisplacementMap`（ブラウザ内蔵）で出る。**依存パッケージ0件を保てる**
- **地図は描画時のフィルタで歪ませてよい。** D7で形を「導出」に決めたため、地図の輪郭にデータの裏付けは要らない
- 色は gamebook の `index.html` の `:root` を引き継ぐ
- **床は透過させる**（作者の要望）
- **炎の揺らぎと陰影を各所に入れる**（作者の要望）。俯瞰の2Dのままでも、放射グラデーション・
  `mix-blend-mode`・マスクで出せる。**three.jsは要らない**（入れると依存0件が崩れる）

**輪郭線だけの案（V10）は不採用。** 作者の判断:「輪郭線の地図でも良いけど、個人的には前の方が好きだな」。

**ただしD9全体が暫定である。** 作者の言葉:「ここは実際の見た目で決めたいです。**isometricと同じ視点にするかも**」。
真俯瞰かアイソメトリックかは、**作って見てから決める**。仕様書で確定させない。

Claudeは「塗りはgamebookの言語（細い線・余白）から外れる」と評価したが、**作者の判断は逆で、
塗りのほうが良い**。この評価は誤りとして取り下げる。

### D12. リリースはスマホのWebアプリ・縦持ち

作者の言葉:「リリースのターゲットはスマホのwebアプリで、**縦持ち**でプレイします（試作は今まで通りブラウザで）」。

- **画面は縦長**。地図の縦横比はこれに合わせる
- gamebookの `index.html` は既に `viewport-fit=cover` と `@media (max-width: 640px)` を持つ（実測）。土台はある
- **three.jsはさらに不利**。スマホで3Dを回すと発熱と電池を食う。俯瞰2Dで光を作る方針は、
  見た目の好みだけでなく技術的にも正しい
- 移動が4方向なので、タップでもスワイプでも入る
- **試作はブラウザで進める。** 縦持ちの実機確認をいつ入れるかは未決

### D11. 一人称視点は、シナリオ進行が起きたときだけ

作者の言葉:「一人称視点は、NPCとの会話や謎、ギミックとの遭遇など、**シナリオの進行が発生した時だけ**ですね」。

- **移動は俯瞰のまま。** 一人称は移動手段ではなく、場面の演出
- ウィザードリィ（一人称で移動・地図は補助）とは逆の構造。理由はD1に書いた通り、戦闘の作業化を避けるため
- 1本目には入らない（物語部屋の接続は2本目）

### D10. パーティは4〜5人（プレイヤー含む）。ただし別モジュール

作者の言葉:「6人は多すぎだと思っています。プレイヤー入れて5人か4人ですね。
キャラ設定、パーティ設定は、また別のモジュールを作るつもりです」。

`PLAN_b1_expedition.md` の未決「パーティを最初から複数人にするか」はこれで解けたが、
**1本目の対象外**。HPを人数分へ広げる作業も、そちらへ送る。

### V2. 方向制約つき生成は成立する

`gen_probe*.mjs`（scratchpad、使い捨て）で計測。

- **実データ『廃坑の灯 rev6』(6部屋): 98.3%（1000seed）**
- 合成データで規則の効きを確認:

| | 素朴な生成器 | 「兄弟の出口に同じ方向語を使わない」 |
|---|---|---|
| 7部屋 | 38.0% | **69.3%** |
| 10部屋 | 8.3% | **44.4%** |
| 14部屋 | 0.7% | **22.6%** |
| 20部屋 | 0.0% | **6.0%** |

低い数字でも問題にならない。衝突は検出できるので、20部屋・6%でも平均17回で当たる（ミリ秒）。

**D4を採ると、この規則自体が不要になる**（絶対方向なら同じ向きの出口は構造的に作れない）。

### V3. 「右」は入口が2つある部屋で必ず壊れる

『廃坑の灯 rev6』の分かれ道は入口が2つある（入り口から来る／崩落した場所から戻る）。

| どこから来たか | 進行方向 | 「右」が指す方向 |
|---|---|---|
| 入り口から | 北 | 東 ＝ 柵のある場所 ✓ |
| 崩落から戻った | 東 | **南 ＝ 何も無い** ✗ |

`灯りの部屋` も同じ（柵から来る／奥の間から戻る）。
**生成器の性能ではなく、相対方向という言葉の性質。手描きしても同じことが起きる。**

### V4. 既存3章は4方向の格子に収まる

1部屋から出る道の最大本数:

| 章 | 部屋 | 最大 |
|---|---|---|

| 渇きの底 | 6 | 3（村の入口・教会） |

### V10. 輪郭線だけの地図（不採用）

- 副産物: 開口部は「未踏の方向」を記号なしで示せる（`?` のようなマーカーを置かずに済む）

**作者の判断で不採用**（D9）。ただし「未踏の出口を壁の切れ目で示す」という発想自体は、
塗りの版でも別の形で使える可能性がある（未検証）。

## 1本目の主題（後回しの未決ではない）

作者の言葉:「霧の規則・部屋の見せ方・炎の揺らぎの具体、これは**めちゃくちゃ重要**だと思っていて、
**これも他のゲームとの差別化になる**と思う」。

Claudeはこの3件を「未決」の欄に置いていたが、**格が違う**。地図が動くことは手段であり、
**1本目の成果物はこの3件の表現そのもの**である（受入条件6がコードで測れないのはそのため）。

| 主題 | いま分かっていること |
|---|---|
| **霧の規則** | 灯りが届く範囲を何で決めるか（部屋単位／距離／視線）。probeの実装は歩いていない通路まで開いており、**間違っていた** |

## 既知の欠陥（probeで発生。1本目で直す）

- **通路の線が部屋を貫通する。** 作者の指摘:「通路の平行線が、部屋と接続しないで
  そのまま部屋の内部まで突き抜けているのは相当おかしい」。**塗り版にも同じ問題がある**（見えにくいだけ）。
  部屋の壁と通路の接合部（開口部）を描く処理が無いのが原因

- 未踏の通路を全長まで薄く描いてしまう。入口だけ見せるつもりだった
