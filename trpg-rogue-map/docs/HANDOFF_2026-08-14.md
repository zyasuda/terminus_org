# 引き継ぎ — なぜこのプロジェクトを作ったか（2026-08-14）

## 出発点

作者が『廃坑の灯』と『渇きの底』を初見でプレイして出た感想。

> 各シーンの位置関係がイメージしづらい。特に初見のユーザーにとってはMAPみたいなものを
> 用意して画像で見せないと位置関係がイメージしづらい。

これが直接の引き金。加えて、第2章を遊んだあとの発言。

> このシナリオでウィザードリイシステムと合体させたゲームでも良い、ほんとそれで遊びたい。

**現行ゲームブックを作り替えるのではなく、独立した遠征モジュールを試す**方針になった。

## gamebookで払った授業料

この5つは、実際に時間を失って学んだもの。同じ穴に落ちないために書き残す。

### 1. 測るまで断定しない

プレイ記録から注文を13件と数え、「10件はデータで直せる」と報告した。
**章データを開いて確かめていなかった。** 実際に当てたら1件も直せなかった。
数え直すと17件で、箱は3つ（データ11／画面3／エンジン3）だった。

同じ日に、複数行にまたがるCSSを1行で検索して「CSSが1つも無い」と報告した。実際にはあった。
**検索が空振りしたことを「無い」と読まない。**

### 2. `npm test` は完了条件ではない

mock2で、テストとビルドが両方緑なのにボタンが物理的にクリックできなかったことがある。
gamebookでも、仕様通りに実装されたのに実際に当てるまで3つの欠陥が見えなかった。

### 3. キャッシュで検証が空振りする

`python3 -m http.server` は `Last-Modified` を返す。編集した分が届かないまま作者が遊び、
4周のうち3周が無駄になった。`serve.py`（`no-store`）を使う。

### 4. UIを足す前に手数を数える

同じ失敗を2回した。決断の選択肢欄と、連鎖の図。どちらも**エンジンのデータの形を
そのまま作者に見せた**。「出来上がりの見本」をチャットで見せて承認を得たが、
壊れたのは表示ではなく**作成**だった（実際は7手・2画面往復）。

**3手を超えるなら設計をやり直す。**

### 5. 作者の作業を失わせない

新しい場面を足すと行き先が無いため検査がエラーを出す。採用直後に赤字で「不整合1件」と
出したところ、作者はどこを直すべきか判断できず採用を取り消し、**3場面分の作業が失われた**。

以後、採用の**前後を比べて増えた分だけ**を報告するようにした。

## 分担（決定）

```
作者      作品としての判断・実プレイ
Claude    設計・仕様書・検証（実ブラウザ）
Codex     実装
```

BORG構想文書 §245 では「Claudeが実装主担当、Codexがレビュー」と書いていたが、
**運用は逆で確定した。** gamebookの直近の作業（記録の読み込み機能）はこの形で通した。

委譲は `gpt-5.6-terra` / reasoning `high` / 非同期。

## 直近の実績（参考になる作りの例）

gamebookの `src/playlog.js` と `docs/SPEC_playlog_review_v1.md` が、この分担で作った直近の1本。
仕様書の粒度、拒否の検査の書き方、実ブラウザ検証の通し方の見本になる。

そこで見つかった、AIに構造化データを出させるときの実測。

- **AIは指示した頭書きを落とす。** `secret:s1a` と書かせても `s1a` と返す（4件中4件）。
  ID自体は正しいので、**エンジン側で吸収する**方が確実
- **同じ入力でも返答がばらつく。** 同じ記録・同じ章で1回目0件、2回目1件
- **何も変わらない案を返してくる**（4件中3件）。押しても変化しないものは出さない
