## `src/mapgen.js`

座標は**区画**単位（D7: 地図は俯瞰）。1区画＝地図の1マス。戦闘の盤面はここでは作らない。

### `makeRng(seed)`

`seed` から決定論的な `() => [0,1)` を返す。同じ seed なら同じ列。

### `linksOf(chapter)`

`scenes[].exits[].to` から**無向**の辺を起こす。

- `to === "ending"` は捨てる
- `a→b` と `b→a` の両方があれば1本にまとめる
- 返り値 `[{ a, b }]`（`a` `b` は `scenes[].id`）

### `depthOf(chapter)`

`scenes[0].id` を起点に、`linksOf` の辺を幅優先でたどった距離。返り値 `{ [id]: 深さ }`。

これがD5の「入口からの遠さの順序」。**生成器が守る唯一の物語上の制約**。

### `generate(chapter, seed, options)`

成功したら地図、失敗したら **`null`**。失敗は異常ではない（V2: 捨てて振り直せばよい）。

```js
{
  rooms:     Map(id → { id, name, x, y, w, h }),   // x,y は左上。区画座標
  corridors: [{ a, b, path: [{x,y}, ...] }],        // 端点の部屋は含まない
  cells:     Map("x,y" → { kind: "room"|"corridor", id? }),
  bounds:    { minX, minY, maxX, maxY }
}
```

`options`（既定値）: `{ roomW: [2,4], roomH: [2,3], gap: [5,8] }`。部屋の幅・高さ・部屋間の距離の範囲。

**手順は2段。閉路があるため、幅優先で置くだけでは足りない。**

1. **全域木を置く。** 未配置の部屋へ繋がる辺を1本ずつ取り、親の部屋から4方向のどれかへ `gap` だけ離して置く。
   `depthOf` が親より大きい部屋は、**入口から遠ざかる向きを優先する**。通路はL字（先に進む向きが選んだ方向）
2. **残りの辺（閉路）を通す。** 両端が既に置かれている辺について、幅優先で経路を探す。
   **他の部屋のマスを通ってはいけない**（既存の通路とは合流してよい）

どちらかで置けなければ `null` を返す。

### 生成器が満たすこと（`test/mapgen.test.mjs` が確かめる）

| # | 条件 | なぜ |
|---|---|---|
| 1 | 全部屋が配置される | — |
| 2 | 部屋どうしが1マス以上離れる | 壁一枚で隣り合うと別々の部屋に見えない |
| 3 | **通路が部屋を貫通しない** | 既知の欠陥の根治。probeで実際に起きた |
| 4 | `linksOf` の全ての辺に対応する通路がある | 閉路を落とさない |
| 5 | 入口から全部屋へ到達できる | — |
| 6 | 同じ seed なら完全に同じ地図 | — |
| 7 | `depthOf` が大きい部屋ほど、入口からの通路の本数が多い（同値は許す） | D5 |

**3が最重要。** これができていないと、部屋と通路の接合部を描けない。

### `generateWithRetry(chapter, seed, maxTries = 200)`

`generate` が `null` を返す間、`seed + 1` で試す。返り値 `{ map, seed }`。
`maxTries` 回とも失敗したら投げる。

実データでの実測は**1発で100%**（2000seed、閉路を含む本当の接続）。再試行は保険。

## `src/expedition.js`

### 移動の単位は「通路1本」

方向を1回選ぶと、**次の部屋まで歩ききる**。1マスずつではない。

- D6が「通路を1本通る＝遭遇の抽選1回」と決めているので、移動の単位と抽選の単位が揃う（3本目でそのまま繋がる）
- スマホ縦持ち（D12）で、長い通路を7回タップさせない

**1マスずつ動く案は採らない。** 上の2つを壊すため。ただし**歩く様子は演出として見せてよい**（灯りが通路を進む）。それは `ui.js` の担当で、状態は行き先に着いた時点で1回だけ変わる。

### `start(map)`

```js
{ at: 入口の部屋id, visited: Set([入口id]), walked: Set(), pos: {x,y} }
```

`walked` は通った通路の集合（`"a-b"` を小さいid順で正規化した文字列）。

### `exitsFrom(state, map)`

いまの部屋から出られる方向。返り値 `[{ dir, to, corridor }]`。
`dir` は `"north" | "east" | "south" | "west"`（**絶対方向。相対方向は使わない — D4**）。

方向は、通路の**最初の1マスがどちらへ出ているか**で決める。

### `move(state, map, dir)`

`exitsFrom` に無い `dir` なら**何もせず `false` を返す**。
あれば `at` を更新し、`visited` と `walked` に足して `true` を返す。

### `lit(state, map)`

見えるマスの集合。**この規則は暫定であり、仕様で確定させない**（→「1本目の主題」）。

初期実装は1つだけ用意する。

- いま居る部屋のマス
- `walked` に入っている通路のマス
- `visited` に入っている部屋のマス
- **いま居る部屋から出ている未踏の通路は、最初の2マスだけ**（そちらに道があることは分かるが、行き先は分からない）

**規則を差し替えられる形にしておく。** 関数1本で完結させ、他から呼ぶのはここだけにする。

# v2 — 歩く（2026-08-14 追加）

v1を実ブラウザで遊んだ作者の指摘による。**v1の仕様を1点撤回する。**

## 撤回: 「移動の単位は通路1本」

v1は「1マスずつ動く案は採らない」と書いた。**理由の1つが誤っていた。**

> D6が「通路を1本通る＝遭遇の抽選1回」と決めているので、移動の単位と抽選の単位が揃う

**移動の粒度と抽選の単位は独立である。** マスごとに歩いても、抽選は「その通路へ初めて入ったとき1回」
で維持できる。3本目の接続は壊れない。

作者の指摘:「通路を一瞬で（それこそローグのように）通り過ぎてしまうので、ゆっくり歩いてほしい。
部屋の中も壁の近くに行ったり、上下左右に動きたい」。

## 変えること

### 1. 移動は1マスずつ

`expedition.js` の `move(state, map, dir)` を **`step(state, map, dir)`** にする。

- 隣のマスが床（部屋または通路）なら、そこへ1マス動いて `true`。壁なら**何もせず `false`**
- `state.pos` が現在地の真値になる。`state.at` は `pos` のあるマスの部屋id（通路上なら `null`）
- `state.visited` / `state.walked` は `pos` の移動にともなって更新する
- **`exitsFrom` は残す。** 3本目（遭遇）が「どの通路へ入ったか」を必要とするため

### 2. 部屋を広げる

いまは `roomW: [2,4]` / `roomH: [2,3]`。**壁際まで歩ける余地が無い。**
`roomW: [4,7]` / `roomH: [3,5]` にする。横縦比の範囲（0.35〜1.0）は変えない。

### 3. 霧を距離で決める

部屋単位ではなくなる。`lit(state, map)` を次に変える。

- **いま見えている範囲**: `state.pos` から一定距離内の床
- **見たことがある範囲**: 一度見えたマスは覚えたまま残す（`state.seen`）。暗く描く
- 部屋に入っただけでその部屋を全部開ける規則は捨てる

**距離の値は決め打ちにしない。** 関数1本にまとめ、差し替えられる形にする（1本目の主題）。

### 4. 画面は現在地に追従する

`viewBox` を地図全体ではなく、**現在地を中心にした固定の大きさ**にする。

- 大きさは画面の縦横比から決める。マス数で持つ（例: 幅18マス）
- **ドラッグで視点をずらせる。指を離してもずらしたまま。**
  現在地へ帰るのは `戻す` を押したときだけ。
  （当初『指を離すと復帰する』と書いたが誤り。それでは見回せず、`戻す` の意味も無くなる）
- **地図のタップでは移動しない。** ドラッグ＝視点、ボタン＝移動。1つの面に2つの機能を置かない

### 5. 灯りに揺らぎ

CSSアニメーションだけで作る。部品を増やさない。

- 明るさと大きさをわずかに揺らす。**周期を一定にしない**（一定だと機械に見える）
- `@media (prefers-reduced-motion: reduce)` で止める
- **文字と地図の可読性を落とさない。** 揺れて読めなくなるなら弱める

### 6. 長押しで歩き続ける

方向ボタンを押している間、一定間隔で `step` を繰り返す。速さは「ゆっくり歩く」が読み取れる程度。
**値は決め打ちにせず、1か所の定数にする。**

## 検査

`test/mapgen.test.mjs` に足す。

- `step` が壁の方向で `false` を返し、`state` を変えないこと
- 部屋の中で上下左右に動けること（幅4以上の部屋で、横に2マス以上動ける）
- 通路を端から端まで `step` で通り抜けられること

`test/screen.test.mjs` に足す。

- 移動しても**移動ボタンが画面内にあること**（既存の6画面で）
- ドラッグで視点が動き、`戻す`で現在地へ帰ること
- **`prefers-reduced-motion: reduce` で揺らぎが止まること**

## v2でもやらないこと

v1の「やらないこと」はすべて有効。加えて:

- 地図のタップによる移動
- 経路の自動探索（目的地を押すと歩いていく）

## 3. 通路と部屋の接触を出入口だけにする（不具合）

**実測（2026-08-14）:**

- 繋いでいない部屋に接している通路: **200seed中18/67 で発生**
- 遊んでいる seed 1 では、6本すべての通路が自分の部屋に **2〜6マス**接している（出入口は1マスであるべき）
- **この制約を満たす地図は 991件中0件。振り直しでは直らない。置き方を変える必要がある**

### 満たすべき条件

```
通路の各マスについて:
  - 繋いでいない部屋のマスと、上下左右で隣接してはいけない
  - 端点の部屋との隣接は、各端で【ちょうど1マス】（＝出入口）
```

### 原因（読んで確認済み）

`treeCandidate` が部屋の縁から出た直後に曲がれるため、通路が壁沿いを走って融合する。
`routeBetween`（閉路用）の幅優先も、部屋の**マス**しか避けておらず、**隣接**を見ていない。

### 直し方（案。これに縛らない）

- 部屋から出たら、**曲がる前に垂直へ2マス以上進む**
- `routeBetween` の通行可能判定を「部屋のマスでない」から「**部屋のマスに隣接しない**」へ変える
  （ただし出入口の前後は例外）

**方法は問わない。上の条件を満たせばよい。** 満たせない場合は `generate` が `null` を返し、
`generateWithRetry` が次のseedを引く。ただし成功率が実用的（数十seed以内で当たる）であること。

### 検査（必須）

`test/mapgen.test.mjs` に足す。**この検査が効くことを、条件を外して赤くなることで確認する。**

- 100seedすべてで、上の2条件を満たすこと
- 生成成功率を出力すること（何seedに1回当たるか分かるように）

# v5 — 光の位置の揺らぎ、通路の自動移動（2026-08-14）

## 1. 光の位置の揺らぎ（不具合修正）

作者の指摘:「位置の揺れはほとんど感じないな。動いてないのでは？」

**実測（ピクセル差分）で確認したところ、実際に動いていなかった。**

原因: `transform: translate(.05px, ...)` の `px` は、viewBoxで拡大されたSVG内では
CSSピクセルではなく**そのSVGのユーザー単位（このアプリでは1マス）**として解釈される。
1マス≈21.6画面ピクセル相当のため、`.05px` は実際には画面上で約1pxしか動いておらず、
ピクセル差分で測ると0だった。

途中、差分測定そのものが0になったため測定方法自体を疑ったが、素のHTMLでの対照実験
（60px移動するdiv）ではハーネスは正しく差分を検出できた。`getAnimations()` でも両方の
アニメーションは `running` で正しく再生されていた。最終的に、最初の確認領域がプレイヤー
座標から外れた場所を切り出していたことが分かり、画面全体で測り直して原因（桁の誤り）を特定した。

**直した:** `torch-sway` の振幅を0.3〜0.6マス相当に上げた。画面全体のピクセル差分で、
毎フレーム約6万ピクセルが変化することを確認済み（実測）。

## 2. 通路は壁か部屋に着くまで自動移動。部屋の中は1マスずつ

作者の要望:「4方向を一度入力したら、通路だったら壁にぶち当たるまで動くのと、
部屋の中だったら、今まで通り1マス移動にしたい」。

### 設計

`step(state, map, dir)`（1マスの純粋な判定）は変えない。既存の検査・呼び出し元が依存しているため。
代わりに `run(state, map, dir)` を新設し、`ui.js` の呼び出し口だけをこちらへ差し替える。

```js
export function run(state, map, dir) {
  const kindAt = () => map.cells.get(keyOf(state.pos))?.kind;
  if (kindAt() !== "corridor") return step(state, map, dir);
  let moved = false;
  while (kindAt() === "corridor") {
    if (!step(state, map, dir)) break;
    moved = true;
  }
  return moved;
}
```

- 現在地が部屋なら、`step` を1回呼ぶだけ（今まで通り）
- 現在地が通路なら、壁に当たるか部屋に着くまで同じ方向へ進み続ける
- **通路の曲がり角では、次のマスが同じ方向に無いため自然に止まる。** 十字路のような分岐判定を別途足す必要はない（通路は幅1マスで枝分かれしないため）
- 長押しは、この `run` を一定間隔で呼ぶだけ。**特別な分岐は不要。** 通路にいる間の最初の呼び出しで一気に走り、部屋に着いた以後の呼び出しは自然に1マスずつになる

### 検証（実測）

- `test/mapgen.test.mjs` に追加。部屋の中でのrunが1マスだけ動くこと、通路でのrunが1マスで終わらないこと、壁でfalseを返し状態を変えないことを確認
- **検査が効くことを確認**: `run` を `step` の別名に一時的に戻すと `v4: 通路のrunは1マスで終わらず、部屋に着くか壁まで進む` で赤くなり、戻すと緑に戻ることを確認した
- 実ブラウザで、同じ方向へのタップを繰り返し、部屋の中は1マスずつ・通路に出た瞬間に走ることを確認した
- `npm test` / `npm run test:screen` とも緑のまま

## v5でもやらないこと

v1〜v4の「やらないこと」はすべて有効。十字路・分岐点での自動停止判定は、
現状の通路が枝分かれしない構造のため不要（今後、通路が分岐する構造を導入する場合は再検討する）。

# v6 — 無関係な通路同士が隣接して抜ける不具合を直す（2026-08-14）

作者の指摘(スクリーンショット2枚): 通路を右へ進むと、隣の通路へ突き抜けて見える。

## 実測（欠陥の再現）

seed=1（アプリが使っている既定seed）で生成した地図を調べたところ、
**通路4と通路6が、`x=18` と `x=19` の列で5マスにわたって隣接**（岩の壁が無い）していた。
`src/draw.js` は通路を太い折れ線として描くため、この隙間の無い隣接が、見た目には
「右へ進んだら別の通路へ繋がっている」ように見える。

200 seedで数えたところ、**16/200（8.0%）の地図で、無関係な通路同士が隣接するマスの組を持つ**
（延べ18組）。v3で直した「通路が無関係な部屋に接する」不具合と同じ種類の欠陥だが、
対象が「部屋」ではなく「別の通路」である点がこれまでの検査で見落とされていた。

## 原因（読んで確認済み）

`src/mapgen.js` の `routeBetween` は、BFSで経路を探す際に**部屋への隣接だけを避けており、
既に配置済みの別の通路への隣接を避けていない**。`blocked` セットは部屋のマスしか持たず、
`touchingRooms` に相当する「別の通路に隣接しているか」の判定が無いため、2本の通路が
1マスの隙間も無く並走できてしまう。

（セルそのものの完全な重複は `generate()` 末尾の `cells.has(...)` チェックで検出されて
生成やり直しになるが、これは「重なり」だけを見ており「隣接」は素通りする。）

## 直すこと

`routeBetween` に、**既に配置済みの通路一覧**を渡し、新しい経路がそれらのマスへ
隣接しないようにする。`touchingRooms`/`hasOnlyDoors` と対になる考え方で、
「通路は無関係な通路にも隣接しない」をBFSの経路探索時点で守らせる
（生成後に検出して作り直すのではなく、そもそも選ばせない）。

- `routeBetween(start, end, rooms, rng)` に、配置済み `corridors` を渡す引数を追加する
- BFSが次のマスを採用する条件に、「そのマスが既存の別の通路のマスへ隣接していないこと」を足す
  （現状の部屋への隣接チェックと同じ考え方でよい）
- `blocked` セット（完全な重複を防ぐ集合）にも、既存の通路のマスを加える
- 呼び出し側（木構造の配置ループ・閉路を作るループの両方）で、既に配置した `corridors` を渡す

## 検査（`test/mapgen.test.mjs` に追加）

「9. 通路は無関係な通路に隣接しない」として、既存の8条件と同じ100 seedループの中で確認する。
判定は「異なる通路に属する2つのマスが、上下左右に隣接していない」こと。

## 検証してほしいこと

- 修正前の状態で、上記の実測（200 seed中16件）を再現できること
- 修正後、同じ200 seedで隣接が0件になること
- **検査が効くことの確認**: 新しい検査を一時的に無効化（または隣接チェックを外した `routeBetween` に戻す）して、
  実測で見つかったseed（またはそれに相当する隣接）が赤くなることを確認してから元に戻す
- 生成成功率（直接生成できる割合、最大再試行回数）を測り、著しく悪化していないかを報告する
  （悪化すること自体は問題ではない。再試行で吸収できるかを見る）
- `npm test` / `npm run test:screen` が緑のまま
- 実ブラウザで、報告のあったseed=1の通路を実際に歩き、隣の通路へ抜けないことを確認する

v1〜v5の「やらないこと」はすべて有効。通路の太さ・岩肌の歪み具合（`src/draw.js`）は変えない。

# v7 — 壁の厚みと倒し込み（2026-08-14）

作者が試作（`probe/tilt.html` の4案比較、`probe/tilt-tune.html` の実機調整）を見て**D案**を選び、

## 決まったこと

| 項目 | 値 | 出どころ |
|---|---|---|
| 倒し込み（`rotateX`） | **24°** | 作者が実機で調整 |
| 遠近の強さ（`perspective`） | **2600px** | 同上 |
| 拡大（`viewBox` の幅） | **26マス** | 同上 |
| 壁の厚み（落ち影＋照り返し） | **入れる** | 「素晴らしい」 |

**値は1か所の定数にまとめる。** 決め打ちを散らさない（`CLAUDE.md`）。

## 経緯（設計判断の根拠。消さない）

作者から「アイソメトリックへ寄せるか」という相談があった。Claudeは当初「投影は変えない方がよい」と
答えたが、**これは雑だった**。反対の理由は「遮蔽が生まれること」と「北が斜めになること」であり、
**倒し込みはそのどちらも連れて来ない**（北は上のまま、高さのある物が無いので何も隠さない）。
アイソメトリックと倒し込みを別物として切り分けるべきだった。この訂正を記録として残す。

**したがって、この先で「壁を実際に押し出して立体にする」方向へは進まない。**
高さのある物を置いた瞬間、通路の先が物陰に隠れ、地図の役目（現在地・戻り道・未踏の方向が分かる）を失う。
**倒し込みまでが安全、押し出しからは危険**という線引きである。

## 1. 壁の厚み（落ち影と照り返し）

床の図形に、**灯りの位置から向きを決めた内側の影**を掛ける。太陽のような固定方向にはしない。
持っている灯りが光源であることが、この作品の肝であるため。

- 図形の中心と灯りの位置から向きを出す。向き＝`normalize(図形の中心 − 灯り)`
- **灯りに近い側**の壁の内面は影（暗い）
- **灯りから遠い側**の壁の内面には照り返し（明るい）
- **暖色の照り返しは、いま灯りが届いている層にだけ乗せる。**
  覚えているだけの層は**冷たい灰色の縁**にする。厚みは地形なので常にあるが、暖色は灯りがある時だけ
  （最初の試作では記憶の層にも暖色を乗せてしまい、消えたはずの灯りが残って見えた）

実装は `probe/tilt-tune.html` の `carved()` がそのまま使える。灯りが動くので、**描画のたびに作り直す**。

## 2. 倒し込み

**床のSVGだけ**を `perspective` + `rotateX` で傾ける。three.js は使わない（D12）。

```
舞台（perspective: 2600px）
 ├ 床の層   rotateX(24deg)   ← SVG。傾ける
 └ 文字の層  変換なし          ← ここは傾けない
```

## 3. 部屋名は傾けない（ビルボード）

作者の要望「部屋名が潰れるのは回避したい。文字がスプライトならできるけど」への対応。

**文字をSVGの中に置かない。** 床の中に見えない目印（`<circle r=".02" fill="none">`）だけを置き、
`getBoundingClientRect()` でそれが画面のどこへ落ちたかを測って、傾いていない層に文字を出す。
ブラウザが3D変換後の実座標を返すので、傾きの逆算を自分で書く必要がない。

- 視点が動けば位置も変わるので、**描画のたびに測り直す**
- 画面の外に出た文字は出さない（測った座標で間引く）
- 実測で確認済み: 倒し込みを0/18/30/44°に振っても、文字の変換行列は `matrix(1, 0, 0, 1, …)` のまま
  （平行移動だけ。回転も歪みも無い）

## 4. 保つもの（壊さない）

v4〜v6で入れたものは**すべて維持する**。

- `run()` による移動（部屋は1マス、通路へ出たら壁か部屋まで自動）と長押し
- 現在地への追従、ドラッグで視点をずらす、`戻す` で復帰
- **移動した時だけ**光源の位置が飛ぶ演出（静止中は `translate(0 0)` で不動）
- 明るさの揺らぎと `prefers-reduced-motion` での停止
  （**倒し込みは動きではないので、`reduce` でも傾けたままでよい**）
- 未踏の通路は入口2マスだけ見せる規則

### ドラッグと倒し込みの噛み合わせ（注意）

傾けると、画面の縦方向1pxが地図の1マスに対応しなくなる。24°なら `cos(24°) ≈ 0.913` なので、
**縦方向の移動量を `1/cos(24°) ≈ 1.09` 倍**すればほぼ合う（遠近2600pxは弱いので、この近似で足りる）。
ドラッグした量と地図の動く量がずれていないか、実際に触って確かめること。
