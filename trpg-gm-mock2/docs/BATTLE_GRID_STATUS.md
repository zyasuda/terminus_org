## 進め方の合意(2026-07-27)

- 現行のCombat v1は**リセットして作り直す**。戦闘は独立したシステム・独立した画面とし、mock2本体とは**戦闘前後の状態を受け渡すデータだけ**で接続する
- フェーズごとにブランチを切り、そのフェーズが終わったら`main`へマージして次のブランチを切る(ブランチを長生きさせない)
- 実装言語はまずJS + Three.js。必要になった部分だけ後からRustへ切り出す

### GMと発話の扱い(決定)

現行の「システムが確定 → GMが語る」という大原則をグリッド戦闘でもそのまま引き継ぐ。

| 要素 | 扱い |
|---|---|
| 移動可否・命中・ダメージ・包囲倍率 | **システムが確定**(`src/battle/core.js`)。LLMは介入しない |
| ダメージ・状態変化の説明 | **GMが語る**。ログに残る形で表示する(現行の左パネル「GMの語り」相当) |
| 同行者・敵の発言 | **吹き出し**で表示する(現行の`companionBubbles`と同じ扱い) |

したがって`core.js`は文言を一切持たず、「何が起きたか」を構造化して返すだけにする。語りと描画はその結果を表現するだけで、結果を変えない。

## 動かし方

```bash
npm run dev          # https://localhost:5173/battle を開く
npm run test:battle  # 盤面ロジックの自己チェック(ブラウザ不要)
npm run smoke:battle # ブラウザで描画・操作・交戦まで通るか確認(要 npm run dev)
```

URLパラメータ:

- `?fixture=melee` … 敵と隣接した状態から始まる(交戦中の挙動を毎回同じ手順で確認するため)
- `?seed=42` … 障害物の配置を固定する。無指定なら起動のたびに変わる

### 操作

- 青いマスをクリックで移動、光っている敵をクリックで攻撃(攻撃するとターンが終わる)
- **やり直す**: 手番の開始時点へ戻す。移動した位置も、途中で拾ったコインも元に戻る。手番開始から何も変わっていないときは押せない。攻撃はその場でターンが終わるので、やり直しの対象にはならない
- **最初から**: 押し間違えると戦闘がやり直しになるため、他のボタンから離して右端に置いている
- **霧チェックボックス+強さスライダー(0〜1)**: fogのon/off・強さをその場で調整できる。盤面は作り直さない
- **塵チェックボックス**: 空気感パーティクルのon/off

### Phase 1で実際に動かして分かったこと(と、その調整)

- 盤面・移動・隣接・包囲・命中・敵の接近と攻撃まで、一通り動作することをブラウザで確認した
- **攻撃できる相手が分からない問題**があったため、対象の足元のマスを塗るのをやめ、相手自身を光らせるように直した(マスを塗っても本体の箱に隠れて見えなかった)
- **移動力が広すぎた**: agility7のガレスは移動力6で、8x8の盤面だとほぼ全域が移動先になり、位置取りの意味が薄れていた
  - → 一度は盤面を12x10へ広げたが、**8x8を基本として作り込む**方針に決まったため8x8へ戻し、移動力の側をさらに半分へ落とした。現在は基本1 + agility補正(+1〜+2)で**合計2〜3**。一手で盤面の1/4ほどしか動けないので、どこへ寄るかの判断が効く
- **包囲ボーナスが通常攻撃では効かなかった**: 「2人で囲んでいる(×1.33)」と表示されつつダメージは1のまま(1×1.33の四捨五入で1)。倍率が効くのはクリティカル時だけだった
  - → 基礎ダメージを1固定から**ユニットの`atk`(既定3)**に変えた。倍率に意味のある解像度が生まれ、atk3なら1人3 / 2人4 / 3人5 / 4人6と一段ずつ増える
  - HPも合わせて調整(ガレス16 / リディア14 / 錆喰い10)。片方が一瞬で溶けない程度の長さにした

### 盤面と見た目(2026-07-27)

- **盤面は8x8を基本**とする。素の盤面は全面が床で、遮蔽は起動のたびにランダムに散らす(左右対称だと展開が読めてしまうため)
  - 高さ1.0 = 柱。進入できない
  - 高さ0.25 / 0.5 / 0.75 = 瓦礫。乗り越えられるので進入でき、視線も遮らない。Phase 2で飛び道具の通過率(1−高さ)に効く
  - 配置は決定論PRNG(mulberry32)なので`?seed=`で再現できる。開始位置には置かず、両陣営が行き来できなくなる柱は取り消すため、通り抜け不能な盤面にはならない
- **ユニットの形は箱**(陣営を問わず、高さだけ変える)
  - 一度は味方を円錐+頭の球、敵を三角柱にしてみたが、**Phase 3の判断材料としては箱が正しい**という判断で戻した。2D表現なら箱の各面(前後左右・上)にテクスチャを貼ることになり、3Dモデルならその箱が占める体積にモデルを置くことになるため、どちらの見当もつけやすい

### 同じマスに立てない / 倒れた駒はコインになる(2026-07-27)

**立っているユニットのマスは、通過も着地もできない。**味方どうしのすり抜けも認めない(決定済み)。判定は`occupiedBy()`に集約し、移動可否を見る箇所すべてが同じ規則を使う。

戦闘不能になった駒は**盤面から退き、その場に金色のコイン(地面に寝た薄い円柱)が残る**。

- コインはマスを塞がない。誰でもそのマスへ入れる
- 見た目は立てたコインをY軸でゆっくり回す(拾えるものだと分かるように)
- **通り道にあるコインは通過しただけで拾える**(着地しなくてよい)。そのため`reachableCells`は各マスに`from`を持ち、`pathTo()`で経路を復元してから、通ったマスのコインをまとめて回収する
- 拾った数はHUDに出る。所持品や報酬への接続はPhase 4(mock2本体との受け渡し)で考える

この形にする前は「倒れた駒もマスを塞ぐ」としていたが、コイン化によって塞ぐ必要がなくなった。なお、塞がない実装のまま倒れた駒を盤面に残すと駒どうしが重なる(通し戦闘のシミュレーションで seed2026 のターン29 に再現を確認済み)。重なりを防いでいるのは「立っている駒だけを数え、倒れた駒は盤面から消す」という組み合わせである。

### 高低差(2026-07-27)

瓦礫のマスに乗ったユニットは**その上に立つ**。以前は足元を`y=0`に固定していたため、瓦礫の箱にめり込んで見えていた(実測で修正を確認: 高さ0.5の瓦礫に乗ると駒が22px上がる。理論値21.2px)。演出の輪・ダメージ数値・コインも同じ高さに合わせる。

立ち位置に差ができたので、近接攻撃に高低差の補正を入れた。

| 段差(0.25=1段) | 命中 | 威力 |
|---|---|---|
| +3段(0.75高い) | 出目 +3 | +1 |
| +2段 | 出目 +2 | +1 |
| +1段 | 出目 +1 | ±0 |
| 同高 | ±0 | ±0 |
| −1段 | 出目 −1 | ±0 |
| −2段 | 出目 −2 | −1 |
| −3段(0.75低い) | 出目 −3 | −1 |

- 補正は**DCではなくd20の出目に足す**。こうしないと「出目20はクリティカル、1はファンブル」という取り決めが崩れる。補正で20を超えてもクリティカルにはならず、下から攻めていても出目20はクリティカルになる
- 1段程度の段差は当てやすさだけに効き、2段(0.5)以上で威力にも効く
- 命中したダメージは補正後も最低1
- 設計書の「地形の高さは射線判定に影響させない」という決定とは矛盾しない。**射線と命中補正は別の話**で、「高い所からでも障害物越しには見えないが、当てやすくはなる」という整理

### ヒット演出(2026-07-27追加)

すべて見た目だけの一時的な表示で、`core.js`が確定した結果は変えない。

- 命中位置に広がって消える衝撃の輪(クリティカルは金色で大きめ)
- damage値が浮き上がりながら消える(canvasテクスチャのスプライト)。**外れも`0`として出す**(何も起きなかったのか、判定が走らなかったのかを見分けられるように)
- 被弾したユニットが一瞬光る
- 画面の揺れ(クリティカルは強め)。基本カメラの上に一時的に重ねるだけで、カメラの目標位置は動かさない
- 空振りは薄いグレーの輪と`0`

### 外壁の書き割り(2026-07-27)

盤面の四辺に`PlaneGeometry`を立て、**法線を内側へ向ける**。裏面は描かれないので、カメラ手前側の壁は自動的に消えて盤面が見通せる(ジオラマの書き割りと同じ考え方)。カメラの4方向すべてで、奥側の2枚だけが出る。

材質は`MeshBasicMaterial`(陰影なし)。**当初`MeshLambertMaterial`にしたところ、カメラを180度回すと壁が消えたように見える不具合が出た**。原因はカリングではなく、指向性ライトが+X+Z側から当たっているため、法線が−X/−Zの壁が環境光だけになって背景に沈んでいたこと(法線・表裏・画面内座標を実測して切り分けた)。書き割りは平らに塗った紙なので、どの向きでも同じ明るさで出るのが正しい。

壁は**上ほど見え、下へ向かうほど透過して闇に沈む**(canvasで作った縦グラデーション)。背景が暗いので、透過させた床際がいちばん暗くなる。

CanvasTextureには`colorSpace = SRGBColorSpace`を指定している。**指定しないとcanvasの値が線形として扱われ、出力時のsRGB変換で持ち上げられて、書いた色よりかなり明るく出る。**

四隅の継ぎ目は実測で255階調中5〜7(約2%)の差しか出ておらず、目視ではほぼ判別できないため未対応のままとする。

### 灯り(2026-07-27)

環境光と指向性ライトを落とし、**味方(ガレス・リディア)がランタンを持ち歩く**形にした。敵は光源を持たない。

- 光源はユニットのGroupに入れてあるので、移動すれば明かりも一緒に動く
- 光源は箱の上部(頭のあたり)に置き、光球のオブジェクトは出さない。腰の高さで横にずらしていた頃より、隣の味方のランタンによる白飛びが減った(実測: 明るい面 125→105、暗い面は青が残って 76,83,96 → 42,62,90)
- 倒れると`visible = false`になり、Three.jsは非表示のオブジェクトを走査しないため明かりも消える(実測で盤面全体が25%暗くなることを確認)
- 周期の違う正弦を4つ重ねて明るさを不規則に揺らし、炎のちらつきに見せる
- 明暗はあくまで演出で、射線・命中・視認の判定には一切関与しない

**点光源の`decay`を0(距離減衰なし)にしてあるのが肝。**既定の逆二乗系のままだと、光源のすぐ隣にある持ち主の体だけが白飛びして陣営の色まで失われた。減衰を切ると`distance`の範囲内が一様に照らされ、縁でなめらかに落ちるので、求めていた「周りがぼんやり明るい」がそのまま出る。

なお、Three.jsのレイヤー(`light.layers`)で持ち主だけ照らさないようにする案は**機能しなかった**。ライトのレイヤーはカメラから見た収集可否を決めるだけで、オブジェクト単位の照射可否のフィルタにはならない(実測して確認)。

### 水溜り(移動コスト2倍、2026-07-27)

足元を取られる地形として、水溜りを追加した。`ユーザーの提案どおり、まず移動コストの2倍化だけを先に実装し、事故(足を取られて転ぶ等)は次のフェーズで検討する`という順番で進めている。

- `cell.terrain = { type: "water", moveCost: 2 }`。障害物(柱・瓦礫)とは別レイヤーで、進入は妨げない(`walkable`のまま)
- `scatterWater()`で、障害物の無い床マスにランダムに配置する。障害物のrng(`seed`)とは別に`seed + 9973`を使うので、柱・瓦礫の個数を変えても水溜りの配置だけがずれることはない
- **`reachableCells()`をBFSからダイクストラ法へ変更した**。移動コストが1マス一律ではなくなったため。盤面は最大64マスなので、優先度付きキューを使わない素朴なO(V²)で十分間に合う
- 見た目は床の上に半透明の板を重ねるだけ。床タイル自体の色を変えると、到達可能マスなどのハイライトで上書きされて見分けられなくなるため、別レイヤーにした
- **水面の質感(2026-07-27追加)**: canvasにまだら模様を焼いたテクスチャを貼り、フレームごとにUVオフセットを少しずつずらしてさざ波っぽく見せている(画像ファイルは使わず、ダメージ数値や書き割りと同じ手描きcanvas方式)。輪郭も正方形の板ではなく、角度ごとに半径を揺らした多角形にして、水たまりらしい丸みのある不定形にした。形はマス位置から作る決定論rngなので、同じ盤面なら毎回同じ形になる
  - スクロール速度は最初0.02/0.013(1秒あたりのUV移動量)にしたところ、3秒程度では変化が実測でも小さすぎて(差分1.13)ほぼ気づけなかった。0.05/0.032まで上げ、4秒で差分4.66まで出るようにした
  - 大きさは半径`TILE*0.36×(0.75〜1.15)`(以前は`TILE*0.3×(0.72〜1.12)`)。タイルの縁は越えない範囲でひと回り大きくした
- 移動時、水溜りを通ったかどうかはログに一言添えるだけ(「〜は水溜りに足を取られながら進んだ。」)。移動力の消費自体は`reachableCells`が既に織り込んでいるので、追加で何かを差し引く処理はない

検証: コーナーが一箇所しかない回廊で、水溜りを踏むと移動力を使い切ってその先へ進めないこと、迂回すれば同じ移動力で奥まで届くことをテストで確認。実機でも、ガレスから3マス先(移動力3)の水溜りへ実際に移動し、コストを使い切ってその場で止まることをスクリーンショットで確認した。

**次のフェーズ(未着手)**: 水溜りに入った時の「足を取られる」事故(判定失敗で移動打ち切り、等)。既存の奇襲判定と同じダイスパターンを流用できる見込み。

### 空気感の粒子(2026-07-27)

盤面のルールには一切関与しない、雰囲気だけの演出。地面から少量の塵(既定22個)がゆっくり立ち上り、左右にゆらゆら揺れながら頂点まで来たら地面へ戻ってまた上る、というループ。

- canvasで焼いた柔らかい光点のテクスチャを個別の`THREE.Sprite`(加算合成)で描画。画像ファイルは使わない
- 各粒子は上昇速度・大きさ・横揺れの振幅と周期・位相をそれぞれ乱数で変えてあり、全部が同じ動きに揃って見えないようにしている
- 数を少なめにする(22個)ことと、加算合成+低い不透明度で、主役である盤面・ユニットより目立たないようにした
- 最初はサイズ0.11・不透明度0.55にしたところ、スクリーンショットを拡大してもほとんど見えないほど控えめすぎた。サイズ0.22・不透明度0.85まで上げてようやく視認できる程度にした
- **サイズ・速度をさらに調整(2026-07-27追記)**: サイズは固定0.22→ばらつき0.16〜0.48、速度も0.06〜0.13→0.14〜0.36(頂点到達が約20〜35秒→約7〜19秒)へ。`THREE.PointsMaterial`は全粒子で同じ`size`しか持てない(粒ごとに変えるにはカスタムシェーダーが要る)ため、粒ごとの大きさを出すには個別の`THREE.Sprite`に切り替える必要があった。実測で、変更前は6秒あたりの差分0.925だったのが、変更後は4秒で1.710(1秒あたり約2.8倍)まで速くなったことを確認
- **サイズ・透過・揺れ方を再調整(2026-07-27さらに追記)**: 前回のサイズ(0.16〜0.48)が大きすぎるとの指摘を受け、0.16〜0.18(乱数の掛け算を`*0.32`→`*0.02`)へ大幅に縮小。不透明度も0.85→0.45、canvasのグラデーション自体の濃さも0.9→0.55に下げて、白がくどく見えないようにした。揺れは「ゆらゆら感が足りない」との指摘を受け、X方向だけの単振動からX・Z両方向(周期・振幅を別々に乱数で変える)へ拡張し、円を描くような揺れにした
- **さらにサイズを縮小・速度を落とす(2026-07-27 3回目)**: まだ大きい、逆に速度が全体的に速すぎるとの指摘を受け、サイズを0.16〜0.18→**0.08〜0.10**、上昇速度を0.14〜0.36→**0.05〜0.12**(頂点到達が約7〜19秒→約20〜52秒)へ落とした。実測で5秒あたりの差分が0.849となり、直前の調整(4秒で1.71)よりはっきり遅くなったことを確認
- **透過をさらに強める(2026-07-27 4回目)**: 白がまだ強いとの指摘を受け、canvasグラデーションの濃さを0.55→0.32、`SpriteMaterial`の不透明度も0.45→0.28へ。中心の実質的な不透明度は0.55×0.45≒0.25から0.32×0.28≒0.09まで下がり、うっすら気配が分かる程度になった

### 奥行きの霞み(fog、2026-07-27)

`scene.fog`(`THREE.Fog`)を追加し、盤面の奥ほど背景色に沈むようにした。書き割りの上下グラデーションとは軸が別(fogは奥行き、書き割りは高さ)なので、役割が重ならず共存できる。標準マテリアルは既定でfogの影響を受けるので、`material`側の追加設定は不要。

**一度、near/farの決め方を間違えて全部が霞んでしまった。** 正射影カメラは見た目の大きさこそ距離で変わらないが、`THREE.Fog`は**カメラ位置からの実距離**で効く。盤面の大きさ(`grid.w`/`grid.h`)だけを基準にnear/farを決めたところ、実際のカメラ距離(`CAMERA_DIST`≒20)よりずっと小さい値になり、盤面全体が「farより遠い」判定になって真っ白ならぬ真っ暗(背景色)に沈んだ。

実際にカメラ位置から盤面四隅までの距離を計測(8x8盤面でこの俯角の場合、手前角が約20.6、奥角が約28.7)し、その範囲を挟むように`near = CAMERA_DIST - 1`、`far = CAMERA_DIST + 10`とした。カメラ回転(4方向)で近い角・遠い角が入れ替わるだけで距離の集合自体は変わらないため、どの向きでも同じ設定で機能する。

**トグル+強さスライダーを追加(2026-07-27追記)**: 「暗いとfogの効果が分かりづらい」「オープンなマップなら使えそう」とのフィードバックを受け、検証パネルにon/offチェックボックスと0〜1の強さスライダーを追加した。`fogObj`(`THREE.Fog`インスタンス)は作り直さず常に保持し、on/offは`scene.fog`への参照の付け外し、強さは`fogObj.far`を`CAMERA_DIST+10`(強さ1)〜`CAMERA_DIST+60`(強さ0、実質無効)の間で補間するだけ。盤面を作り直す必要はない。

塵パーティクルにも同様にon/offチェックボックスを追加した。全スプライトを`THREE.Group`にまとめ、`group.visible`を切り替えるだけ。

いずれも演出の見た目調整であり、ゲームの状態ではないため`state`には含めず、`useState`で別管理にしている(「やり直す」「最初から」の対象外)。

**雨・壁トグル・背景色を追加(2026-07-27追記)**: 「屋外マップも表現したい」とのフィードバックを受け、以下を追加した。

- **雨**: 塵と同じ「個別`Sprite`を`Group`にまとめてon/offする」作りをそのまま流用。違いは、上へゆっくり浮くのではなく速く落とすこと(`speed`3.2〜5.4/秒)、粒を縦長の細い筋にすること、量を塵より多くしたこと(90個)。地面まで落ちたら上へ戻す点は塵と同じ考え方。既定はオフ(暗い盤面に降らせると重い印象になるため、屋外マップで使う想定)
- **壁のon/off**: 4枚の書き割り(`PlaneGeometry`)を`backdropGroup`という`THREE.Group`にまとめ、`group.visible`で切り替えるだけ。壁自体の作りは変えていない
- **背景色**: `<input type="color">`で選べるようにした。`scene.background`と`fogObj.color`を同じ値にそろえている。片方だけ変えると、fogが奥で「元の暗い色」に沈んでしまい、背景だけ空色でも奥だけ暗く見えてしまうため

いずれもPlaywrightで見た目を確認済み(雨on+空色背景+壁offで、書き割りが消えて空色の背景に雨が降る画面になることを確認)。壁のグラデーションテクスチャは元の暗い背景色を前提に焼いてあるので、明るい背景色(空色)にすると壁の色味がやや浮いて見える。気になる場合は壁色も背景色に連動させる余地があるが、今回は要望に出ていないので手を付けていない。

**雨の落下速度を調整、光の「昼/夜」プリセットを追加(2026-07-27追記)**: 雨の落下速度が速すぎるとの指摘を受け、`speed`を3.2〜5.4/秒から1.6〜2.8/秒へ半分程度に落とした。

また「屋外なら太陽光のようなものも要るのか」という質問に対し、要る(背景色だけ変えても地面の明るさは変わらず浮いて見える)と回答し、プリセット形式での実装に合意を得た。`AmbientLight`と`DirectionalLight`の強さ・色をあらかじめ`night`(既定、現状の暗めの値)と`day`(環境光0.85・指向性光1.05、色も暖色寄りに)の2組で持っておき、HUDの`<select>`で切り替えるだけの実装。ライトのインスタンス自体は作り直さず、`intensity`と`color`を書き換えるだけなので盤面を作り直す必要はない。Playwrightで昼プリセット時に地面・障害物が明るく照らされることを確認した。

**ランタン光源・障害物・水溜りのon/offを追加(2026-07-27追記)**: 検証パネルがここまで揃ったので、ついでに残っていた見た目要素も同じ考え方でトグル可能にした。

- **障害物**: 柱(進入不可)と瓦礫(乗り越え可)のメッシュを`obstacleGroup`(`THREE.Group`)へまとめてon/off。地形本体の境界壁(現状未使用)は含めない
- **水溜り**: 水面メッシュを`waterGroup`にまとめてon/off
- **ランタン**: 各ユニットの`PointLight`は個々のユニットGroupの子なので、壁や塵のように単一のGroupへはまとめられない。代わりに`lanterns`配列に集めたlightへ直接`visible`を立てる方式にした。ユニットは手番描画時に遅延生成されるため、生成タイミングによらず設定が効くよう`lanternsOn`という状態をシーン内に持ち、新しいランタン生成時にもその値を初期値として使う

いずれも見た目だけの切り替えで、`grid`側の当たり判定・移動コストはそのまま残る(非表示でも柱は通れない、瓦礫上には乗れる、水溜りの移動コスト2倍も変わらない)。Playwrightで全offにした状態のスクリーンショットを確認し、柱・瓦礫・水溜りが消えてランタンの明かりも消灯し、盤面が均一な暗さになることを確認した。

**検証パネルの既定値をすべてoffに変更(2026-07-27追記)**: 霧・塵・雨・壁・ランタン・障害物・水溜りのトグルは、すべて既定offとした(光は元々「夜/夜昼」の選択式なので対象外、背景色ピッカーも同様)。まっさらな状態から必要な演出だけ足していく確認をしたいという要望による。ゲームのルール(移動コスト・当たり判定)はトグルの見た目とは独立しているので、表示offでも柱は通れず水溜りの移動コストも2倍のままである点は変わらない。

**柱の下の床の隙間を修正、「穴」トグルを追加(2026-07-27追記)**: 柱(進入不可の障害物)のマスは、旧実装では床タイルの生成自体をスキップ(`continue`)していたため、柱の底面と周囲の床の間に背景色が透けて見える隙間ができていた(スクリーンショットで指摘を受けて発覚)。柱のマスにも通常の床タイルを敷いて隙間を塞いだ。

ただし「床がないいわゆる穴の見た目も面白い」とのことだったので、削除はせず`groundPatchGroup`という別Groupに床タイルをまとめ、「穴」チェックボックスでon/offできるようにした(on=床を隠して穴に見せる、off=床が敷かれた通常状態。既定はoff)。既存の「障害物」トグル(柱・瓦礫の表示)とは独立しているので、柱を隠したまま穴だけ見せる、柱を出したまま床だけ抜く、のどちらの組み合わせも作れる。空色背景で柱の下にうっすら背景色が覗く見た目をPlaywrightで確認した。あくまで見た目だけの切り替えで、柱の当たり判定自体は変わらない(「穴」に落ちる、というゲームルールは今回実装していない)。

**霧の色を背景色と切り離した(2026-07-27追記)**: 「霧を白っぽくしたい」との要望を受けて確認したところ、`setBackgroundColor`が背景色と一緒にfogの色まで書き換える実装になっており(奥で背景色に溶け込ませる意図だった)、霧だけ別の色にすることができなかった。`setFogColor(hex)`を新設して背景色とは独立に持たせ、HUDの霧の行に専用の`<input type="color">`を追加した。既定値は背景色初期値と同じ(#161a22)にしてあるので、これまでの見え方は変わらない。Playwrightで霧を白(#f2f2f2)にし、背景は暗い紺のままで奥だけ白く霞むことを確認した。

**霧のフェーダーの粒度を修正(2026-07-27追記)**: 「50%以上は変化が粗く、50%以下はほとんど反映されない」との指摘を受けて調査。原因は、フェーダーの値`t`を`fogObj.far`へ**等間隔**で反映していたこと。`THREE.Fog`の不透明度は`(far-距離)/(far-near)`で決まる比率なので、盤面奥での実際の霞み具合(density)は`(D-near)/(far-near)`という**反比例**の関係になり、farを等間隔にずらしてもdensityは強さの高い側(far がnearに近い側)でしか大きく動かず、低い側ではほとんど動かなかった。

修正として、盤面奥角の実測距離(`FOG_REF_DIST`、約28.7)での霞み具合(density)をスライダー`t`に対して**線形**になるよう先に決め(`FOG_MIN_DENSITY`0.05〜`FOG_MAX_DENSITY`0.88、最大値は従来のfar=CAMERA_DIST+10と同じ見え方になるよう合わせた)、そこから`far = near + (D-near)/density`で逆算する方式にした。Playwrightで背景色をやや明るいグレーに変えたうえで盤面奥角付近のピクセル輝度をt=0/0.25/0.5/0.75/1で測定し、各区間の変化量がほぼ均等(19%/24%/26%/30%、以前は変化が高強度側に極端に偏っていた)になったことを確認した。

- **包囲ボーナスの倍率**: 設計書どおり1 + (人数−1)/3。基礎ダメージを`atk`にしたことで一段ずつ増えるようになったが、数値そのものは仮置き
- **ダメージとHPの数値**: atk(ガレス3 / リディア2 / 錆喰い2)、HP(16 / 14 / 10)、`defenseDc` 12(d20で45%命中)。1体を倒すのに4回前後の命中が要る想定
- **斜め移動のコスト**: 1マス1コスト(チェビシェフ距離)。近接射程が8方向隣接なので移動も8方向で揃えた。斜めを1.5にしたい場合は`reachableCells`だけ直せばよい
- **他ユニットのマス**: 立っている駒は通過も着地も不可(味方も含む・決定済み)。倒れた駒はコインになり塞がない
- **移動力**: 基本1 + agility補正(7以上=+2 / それ未満=+1)。8x8に対して合計2〜3。盤面が広がったら段を増やす
- **障害物の数**: 柱5・瓦礫6(8x8=64マスに対して約17%)
- **水溜りの数**: 4(8x8=64マスに対して約6%)、移動コストは一律2倍

## 防御・リアクション(パリィ/いなす/カウンター/ドッジ、2026-07-27設計・実装)

近接をもう少し作り込みたいという話から、防御系のアクションを検討した。パリィ・いなす・カウンター・ドッジに加えて「単純な防御」「体当たり」「跳躍」「背後を取る」なども候補に挙がったが、実装難度で分けて優先順位を決めた。

- **すぐ乗る**: 防御・体当たり・クリティカル狙いなど、既存のターン制のまま追加の判定だけで済むもの
- **中くらい**: 背後を取る(ユニットに向きの概念が要る)、跳躍(移動の特例)
- **一番重い**: パリィ・いなす・カウンター。本来は「相手の攻撃に割り込んで反応する」もので、今の決定論的な「自分のターンに行動→ターン終了」という流れの外側の仕組み(割り込み処理)が要る

割り込み処理は当初「敵の攻撃時に一時停止してプレイヤーに選ばせる」案で考えたが、採用しなかった。理由は次のとおり。

**採用した設計: 事前コミット方式**。プレイヤーは自分のターンで、移動・攻撃の代わりに「防御」を選び、パリィ/いなす/カウンター/ドッジのどれで構えるかをその場で決める。敵の攻撃はそれ以降、自動解決の中で構えの内容に従って処理されるだけなので、**敵ターンの自動解決を止める処理が不要**になる。既存のターン構造(プレイヤーの手番はインタラクティブ、敵の手番は自動)を一切変えずに実現できる。

引き換えに、「その場で見てから反応する」駆け引きではなく「今回はこの構えで行く」という事前コミットの駆け引きになる(多くのタクティクスゲームでも一般的な形なので許容)。

各リアクションの仕様(`guard: { type, used }`をユニットに持たせ、選んだ本人の次の自分の手番まで、または使い切るまで有効):

- **いなす(deflect)**: 何度でも使える。ダメージを1点軽減するだけ(無効化はしない)
- **パリィ(parry)**: guard中1回だけ。防御ロール(d20 ≥ 相手のdefenseDc)に成功すれば攻撃を完全に無効化。成否にかかわらずその場で使い切る
- **カウンター(counter)**: 防御ロールに成功した時だけ発動し、成功時のみ使い切る(失敗した場合は消費されず、次の攻撃でまた試せる)。成功すると攻撃を無効化した上で即座に反撃する
- **ドッジ(dodge)**: 使用回数ではなく地形条件。隣接8マスに「歩行可能・誰も立っていない・障害物の高さが0.5未満」のマスが1つでもあれば、その攻撃を自動的に外す。地形さえ許せば何度でも成立する

guardは、その本人が次に自分の手番で移動・攻撃という行動を取った時点で解除される(選び直さない限り、防御の構えは自分の番が回ってくるまで有効という扱い)。

**実装した**。`core.js`に`hasEscapeRoute`と、`resolveMelee`の`guard`引数(反応の判定・消費・カウンターの反撃ロールまで)を追加し、`core.test.mjs`にドッジの逃げ道判定・4種のリアクションそれぞれの単体テストを足した(`npm run test:battle`で全チェック通過)。`BattleView.jsx`には防御の構えを選ぶ4つのボタンと、ユニットのHP表示に構え・使用済みかどうかを添えるチップ表示を追加した。攻撃の解決(`attack`関数)は、通常のダメージ適用とカウンターの反撃ダメージ適用を`applyDamage`という共通処理にまとめ、倒れた場合のコイン処理も両方でそのまま使い回している。

Playwrightで実際に4種類すべてを操作して確認した: ドッジは地形が許す限り毎回「身をかわした」と出て被弾しないこと、いなすは被弾しつつ1点軽減されチップの構え表示が消えない(使い切らない)こと、パリィは1回発動した時点でチップが「パリィ済」に変わり以降は通常どおり被弾すること、カウンターは防御ロール成功時だけ「カウンター済」になり反撃(命中/外れ)が起きることを確認した。

**改名と成功表示(2026-07-27追記)**: 「パリィと受け流しは紛らわしい」との指摘を受け、`受け流し(deflect)`の表示名を**いなす**に変更した(内部の識別子`type: "deflect"`自体は変えていない、表示名だけの変更)。あわせて「防御が成功したら分かりやすく表示してほしい。失敗はダメージが入ることで分かるので、あえて書かなくてよい」との要望どおり、各リアクションが成功した時だけログに`◯◯、成功。`と明示するようにした(ドッジ・いなす・カウンターは発動した時点で必ず成功、パリィだけ「試みたが防御ロールに失敗し通常どおり被弾」の場合があるので、その場合は成功タグを出さない)。

**ドッジ成功時に実際に間合いの外へ移動するよう変更(2026-07-27追記)**: 「ドッジ成功したら、敵と隣接しないグリッドに移動して欲しい」との要望を受け、`hasEscapeRoute`(逃げ道の有無を返すだけ)を`findDodgeCell`に置き換えた。単に空きマスへ避けるだけでは同じ攻撃者にまた狙われ続けてしまうため、成立条件を「targetの隣接マスのうち、歩行可能・誰も立っていない・障害物の高さが0.5未満・**かつattackerとも隣接しなくなる**マス」に変更し、見つかった座標(`dodgeTo`)を`resolveMelee`の返り値に含めた。`BattleView.jsx`はドッジ成功時に`target`の座標をその`dodgeTo`へ実際に更新する。

この変更で、盤の端にいて「攻撃者から離れた側」に逃げ場が無い場合はドッジが成立しなくなる(以前は単に空きマスがあれば常に成立していた)。`core.test.mjs`のテストも、単発の空きマスチェックから「attackerと隣接しなくなるか」を検証する形に書き直した。Playwrightで、ドッジ成功時にログへ「◯◯の間合いの外へ跳び退いた」と出て、実際に元の攻撃者と隣接しない位置へ移動することを確認した。

## 薙ぎ払い(2026-07-27設計・実装)

「複数に隣接している場合の広範囲攻撃をやりたい」との相談を受け、実装まで一任された。既存の`resolveMelee`が1体ずつの解決を担う純粋関数だったため、`resolveSweep`はそれを**隣接する敵全員に対して1体ずつ呼び出すだけの薄い層**として実装できた。命中判定・高低差・防御の構え(パリィ/いなす/カウンター/ドッジ)は各対象に個別にそのまま効く(片方はいなして軽減、もう片方はカウンターで反撃してくる、といったことが自然に起こる)。

- 出目は**1回だけ共有**する(全員に同じ出目で判定。高低差の補正だけ相手ごとに変わるので、命中/クリティカル/ファンブルの結果自体は相手ごとに変わり得る)
- パリィ・カウンターの追加の防御ロールは対象ごとに独立(共有はしない)。同じ`roll()`を使うが、各対象内では「最初の1回だけ共有出目、以降は新しく振る」という薄いラッパーで実現した
- ダメージは通常攻撃(1対1)より弱くする。今回は**一律0.6倍**(`SWEEP_DAMAGE_MULTIPLIER`)を仮に採用。数値は遊びながら再調整する前提
- HUDには「薙ぎ払い(隣接数)」ボタンを追加。隣接する敵が2体以上の時だけ有効(1体なら通常攻撃の方が強いので選ぶ意味が無い)

`core.test.mjs`に、隣接する複数体だけが対象になること・全員が同じ出目で判定されること・対象ごとの防御の構えが独立して効くこと・ダメージが0.6倍になることのテストを追加。`BattleView.jsx`側は、通常攻撃とロジックを共有するため、防御反応ごとのログ生成処理(`applyMeleeResult`)と演出処理(`playHitEffects`)を共通化し、`attack`と`sweep`の両方から呼び出す形にリファクタリングした。Playwrightで実際にボタンを操作し、共有出目での同時判定・ログ整形を確認した。

## 体当たり・クリティカル狙い(2026-07-27設計・実装)

「近接の残り(すぐ乗る候補)」として、以前保留していた2つを実装した。どちらも「攻撃」の代わりに選ぶ行動で、選んでから相手をクリックすると発動し、使うと自動的に「通常」へ戻る(防御の構えのように持ち越さない)。

**体当たり**: `resolveShove`は`resolveMelee`をそのまま呼び出して命中判定・防御の構え(ドッジ・パリィ・カウンター)を丸ごと再利用し、命中した場合だけダメージの代わりに押し出しへ差し替える薄いラッパー。attacker→targetの延長線上の隣接マスへ押し出し、そのマスが壁・障害物(高さ1以上)・他ユニット・盤外のいずれかで塞がっていれば押し出せず、ダメージ1点だけ入る(数値は仮置き)。ドッジ・パリィ・カウンターが成立すれば`resolveMelee`側でhit=falseになり、体当たり自体が不成立になる(他の近接攻撃と同じ挙動)。

**クリティカル狙い**: `resolveMelee`に`critMin`(既定20)・`fumbleMax`(既定1)という2つの引数を追加した。通常攻撃は既定値のままなので挙動は変わらない。クリティカル狙いはこの2つを`critMin:18, fumbleMax:3`で呼び出すことで実装し、出目18〜20でクリティカル・出目1〜3でファンブル扱いになる(範囲がそれぞれ3倍に広がる)。「一撃に賭ける」という趣旨どおり、命中しやすさそのものは変えず、当たれば/外れれば双方の振れ幅が大きくなる形にした(既定のDC判定は4〜17の間だけ従来どおり)。

`BattleView.jsx`には攻撃モードの選択行(通常/体当たり/クリティカル狙い)を追加し、`attack`は`resolveMelee`への追加オプション(`meleeOpts`)を渡せるように変更した。`applyMeleeResult`には、`resolveShove`の返り値に含まれる`pushedTo`キーの有無で体当たりの結果と判定し、押し出し成功/失敗それぞれのログを組み立てる分岐を追加した。`core.test.mjs`に、押し出しの成功・障害物/他ユニット/盤外による失敗・ドッジとの相互作用、およびクリティカル狙いの拡大判定のテストを追加。Playwrightで実際に体当たりモードを選んで敵をクリックし、「弾き飛ばした」のログと共に押し出しが発生することを確認した。

## 「最初から」でステージ設定もランダム化(2026-07-27)

「最初からボタンを押すと、ステージ設定のパラメータをランダムで決めたい」との要望を受け、`restartWithRandomStage`を実装した。対象は背景色(あらかじめ用意した色候補から選ぶ。任意のRGBだと読みにくい配色になり得るため)・昼夜・壁の有無・障害物の有無・水溜りの有無・穴の有無。**穴は障害物(柱)がある時だけランダムにする**(柱の下の隙間という演出なので、柱自体が無ければ意味を持たない)。

霧・塵・雨はランダム化の対象に含めなかった。この画面の主目的は地形・障害物・時間帯といった舞台構成を色々な組み合わせで確認することで、霧や雨をランダムに乗せると、それらの見え方自体を隠しかねないため。強さ(フェーダー・色)も含めて手動で調整する検証パネルとして、そのまま残している。

Playwrightで「最初から」を繰り返し押し、壁・障害物・水溜り・背景色・昼夜がそれぞれ変わること、障害物off時は穴が常にoffになることを確認した。

**背景色を暗めに限定、ガレス・リディアの身長を縮小(2026-07-27追記)**: 背景色の候補が明るすぎるとの指摘を受け、`BG_COLOR_CHOICES`をすべて明度(HSLのL)50%以下の暗い色に差し替えた(Playwrightで実際にHSLのLを算出し、全候補が26.7%以下であることを確認)。あわせて、ガレス(身長2→1.5)・リディア(1.9→1.425)を約75%に縮小した(敵の錆喰いは0.8のまま)。

## 盤面サイズも8〜12でランダム化(2026-07-27)

「マップグリッドも8x8から12x12のランダムにしたい」との要望で、盤面サイズ(8〜12の正方形)を`seed`から決めるようにした。今までは`BASE_MAP`が8x8固定の定数だったが、`baseMapFor(size)`で都度組み立てる形に変えた。

- **サイズの抽選**: `boardSizeFor(seed)`は`seed+4242`をオフセットにした別ストリームの乱数器で8〜12の整数を選ぶ。障害物・水溜りの抽選(`seed`本体・`seed+9973`)とは独立しているので、サイズの抽選がそれらの配置を狂わせない
- **障害物・水溜りの密度**: 絶対数(柱5・瓦礫6・水4)のままだと盤面が広がるほどスカスカになるため、8x8(64マス)での比率に揃えて面積比でスケールするようにした(`Math.round(面積 × 元の数 / 64)`)
- **開始位置**: 従来は8x8前提の絶対座標(例: `[7, 3]`)で持っていたが、盤面サイズからの相対位置(`[size-1, Math.floor(size/2)]`等)で計算する形に直した。`?fixture=melee`(隣接開始)もサイズによらず中央付近で隣接するように再定義した
- 検証用に`?size=`パラメータを追加(`?seed=`・`?fixture=`と同じ位置づけ)。無指定ならseedから自動で決まる

Playwrightで`?size=12`・`?size=8`それぞれが正しく描画されること、同じ`?seed=`なら2回読み込んでもほぼ同一の画面(ピクセル差18/225万、アニメーション位相程度)になり盤面サイズも再現されることを確認した。移動力(`movePointsFor`)は8x8向けにチューニングされた値のままなので、12x12だと相対的に移動が重く感じられる可能性がある。数値の再調整は保留。

## 長方形化・外形の変形(角を削る/辺に切れ込み、2026-07-27)

「正方形である必要はあるか」との質問に対し、`core.js`の`createGrid`はもともと行ごとに長さの違う配列(可変形状)も扱える設計で、`view3d.js`もカメラ・書き割り壁とも`grid.w`/`grid.h`を別々に見ているため、正方形は制約ではなく実装上の単純化だったと回答した。続けて「長方形にしたい、角が大きく抉れていたり辺がうがっていたりする変形バリエーションも欲しい」との要望を受けて実装した。

- **長方形化**: `boardSizeFor(seed)`(1つの値)を`boardDimsFor(seed)`(`{w, h}`)に変更。幅・高さをそれぞれ独立に8〜12から選ぶ(同じ乱数器から2回連続で引くので、`w`と`h`が偶然一致することはあっても機構としては独立)。`?w=`/`?h=`パラメータも追加(`?size=`は廃止)。開始位置(`START`)も幅・高さそれぞれの相対位置で計算するよう直した
- **外形の変形**: `carveShape(grid, rng, { keepClear })`を新設。「角を大きく削る」「辺の中央に切れ込みを入れる」「変形なし」をランダムに1つ選ぶ。削ったマスは`walkable: false`にした上で、新設した`cell.void = true`を立てる。**柱・地形の壁(obstacle)とは別の「そもそも盤面の外」という扱い**にしたのがポイントで、`view3d.js`側は`void`のマスに何も描画しない(壁の見た目も床のパッチも出さない、完全な空白)。既存の柱(`obstacle`)は変わらず壁の見た目つきで描画される
- 削る範囲はkeepClear(開始位置)を避け、既存の`scatterObstacles`と同じ考え方で、削った結果keepClearの両端が行き来できなくなる変形は取り消す(接続性を壊さない)
- `core.test.mjs`に、角削り/辺切れ込み/変形なしそれぞれのジオメトリ、keepClearの保護、複数seedでの「keepClearは常に無傷」「変形後も両端は必ず到達可能」という不変条件のテストを追加

見た目の確認は、目視だけでなく`window.__debugGrid`という一時的な診断フック(検証後に完全に削除・grep 0件を確認済み)でグリッドの`w`/`h`/`void`セル数を直接読み取り、30seed中約半数で変形が発生していること、空色背景に変えた上で実際に角の抉れ・辺の切れ込みが背景色の透過として見えることをスクリーンショットで確認した。
