設計の正本は `docs/BATTLE_GRID_DESIGN.md`。このファイルは「今どこまで終わったか」を追うための作業用メモで、フェーズが進むたびに更新する。

最終更新: 2026-07-27

## 進め方の合意(2026-07-27)

- 現行のCombat v1は**リセットして作り直す**。戦闘は独立したシステム・独立した画面とし、mock2本体とは**戦闘前後の状態を受け渡すデータだけ**で接続する
- フェーズごとにブランチを切り、そのフェーズが終わったら`main`へマージして次のブランチを切る(ブランチを長生きさせない)
- 実装言語はまずJS + Three.js。必要になった部分だけ後からRustへ切り出す

### GMと発話の扱い(決定)

現行の「システムが確定 → GMが語る」という大原則をグリッド戦闘でもそのまま引き継ぐ。

| 要素 | 扱い |
|---|---|
| 移動可否・命中・ダメージ・包囲倍率 | **システムが確定**(`src/battle/core.js`)。LLMは介入しない |
| ダメージ・状態変化の説明 | **GMが語る**。ログに残る形で表示する(現行の左パネル「GMの語り」相当) |
| 同行者・敵の発言 | **吹き出し**で表示する(現行の`companionBubbles`と同じ扱い) |

したがって`core.js`は文言を一切持たず、「何が起きたか」を構造化して返すだけにする。語りと描画はその結果を表現するだけで、結果を変えない。

## 動かし方

```bash
npm run dev          # https://localhost:5173/battle を開く
npm run test:battle  # 盤面ロジックの自己チェック(ブラウザ不要)
npm run smoke:battle # ブラウザで描画・操作・交戦まで通るか確認(要 npm run dev)
```

`/battle?fixture=melee` を付けると、敵と隣接した状態から始まる(交戦中の挙動を毎回同じ手順で確認するため)。

### Phase 1で実際に動かして分かったこと

- 盤面・移動・隣接・包囲・命中・敵の接近と攻撃まで、一通り動作することをブラウザで確認した
- **攻撃できる相手が分からない問題**があったため、対象の足元のマスを塗るのをやめ、相手自身を光らせるように直した(マスを塗っても本体の箱に隠れて見えなかった)
- **移動力が広すぎる**: agility7のガレスは移動力6で、8x8の盤面だとほぼ全域が移動先になる。盤面を広げるか移動力を下げるかの判断が要る
- **包囲ボーナスが通常攻撃では効かない**: 実測で「2人で囲んでいる(×1.33)」と表示されつつ、ダメージは1のまま(1×1.33の四捨五入で1)。倍率が効くのはクリティカル時だけになっている

## 仮置きの値・後で調整する判断

実装は入れたが、手触りを見て変える前提のもの。

- **包囲ボーナスの倍率**: 設計書どおり1 + (人数−1)/3。ダメージは四捨五入するため、1ダメージ×1.33は1のまま(2人でも増えない)、クリティカル2ダメージ×1.33で3になる。刻みが粗いので、HP設計と合わせて要調整
- **斜め移動のコスト**: 1マス1コスト(チェビシェフ距離)。近接射程が8方向隣接なので移動も8方向で揃えた。斜めを1.5にしたい場合は`reachableCells`だけ直せばよい
- **他ユニットのマス**: 通過も着地も不可。味方のすり抜けを許すなら`reachableCells`の`blocked`の作り方を変える
- **移動力の基本値3**: agility 4〜7 に対して合計4〜6マスになる。マップの広さを決めてから再調整する
- **agility → 移動力ボーナス**: 4以下=+1 / 5〜6=+2 / 7以上=+3 の3段階
