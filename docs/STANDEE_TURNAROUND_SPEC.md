# スタンディー二面図の仕様と受け入れ検査

対象: リディア・ガレスなど、アイソメトリック盤面で**透明アクリル板の駒**として使う
キャラクター。前面(正面)と背面の2枚の人物絵から、厚みを持つ1個のソリッドを作る。

このドキュメントは、二面図を**作る前**と**3D化する前**に読む。

---

## 1. なぜ二面図の「対応」が必要なのか

アクリル板の駒は、**1枚の板の前後に絵を印刷したもの**である。板の外形は前後で
共通で、1つしか作れない。

そのため、前後のシルエットが食い違うと、その差が**そのまま「人物のいない余白」**
になる。板の作り方を工夫しても消えない。実際に3通り試して、いずれも解決しなかった。

| 外形の作り方 | 結果 |
| --- | --- |
| 前面のシルエットだけを使う | 背面から見ると絵が板の外に出る(ガレスで背面の16%がはみ出し) |
| 前面と背面の**和** | 片側だけ余白が膨らむ。「右肩の余白が大きい」の原因 |
| 前面と背面の**符号付き距離場の平均** | 余白は均等化されるが、前後差の半分が余白に乗る |

距離場の平均を使った時点でのガレスの余白(目標29px):

```
y      左余白  右余白
  320     66      30    ← 腕組みの肩。目標の2.3倍
  420     54      15
 1020     37      61
 1320     55      31
 1620    285      43    ← 足の高さの差
```

前後差が66pxあれば、平均を取っても余白は 29 + 33 = 62px になる。**絵の側で対応を
取る以外に方法がない。**

## 2. 受け入れ基準

`scripts/check-standee-pair.mjs` が機械的に判定する。許容値はすべて**人物の高さに
対する比**で持つ(元絵の解像度がキャラごとに違うため)。

### 合否を決める項目

| 検査項目 | 上限 | 意味 |
| --- | --- | --- |
| 余分な余白の面積(前面/背面) | 5% | 板の面積のうち、狙いの余白より広く空いた割合 |
| 余白の超過(前面/背面) | 3% | いちばん広く空いた場所が、狙いの余白を何px超えたか |
| 前面の反転アルファとの一致 | 99.5% | 100%なら前面のシルエットで型抜きしただけ。第8.6節 |

狙いの余白は `standee-lib.mjs` の `MARGIN_RATIO`(現在 **3%**)。

**合否は「板に出る余白」で決める。** 作者が見るのは板の余白であって、シルエットの
一致率ではない。板の外形は前後の距離場の平均で作るので、前後のずれは両面で折半
される。実測すると、シルエットのXORが20%でも余分な余白は4%程度にしかならない。

上限は 2026-08-25 に実測から決めた。採用した2体が通り、腕組みと下ろした腕で
明らかに食い違うガレスv11が落ちる水準にしてある。

**「余白の超過」は狙いの余白を引いた値で測る。** 距離の絶対値で測ると、
`MARGIN_RATIO` を広げただけで数値が悪化して不合格になる(1.9%→3%にして実際に起きた)。
測りたいのは前後のずれであって、余白の広さではない。実際、超過量は余白を広げる
前後で変わっていない(リディア前面 39px のまま)。

### 参考値(合否には使わない)

余白が上限を超えたとき、**どこを直せば減るか**を調べるために出す。

人物高さの差 / 輪郭のずれ 中央値・p95 / シルエットの食い違い(XOR) /
足の横位置のずれ / 靴底の高さのずれ

さらに**警告**として、透明部分の色が人物の縁から離れていないかを見る(第9節)。
`build-standee-acrylic.mjs` が自動で直すので、警告が出ても作業は止めなくてよい。

いずれも、**背面を左右反転し、頭頂・足元・胴の中心を前面へ合わせた後**に測る。
制作パイプラインと同じ正規化を通す。

### なぜ合否をXORから余白へ変えたか(2026-08-25)

XOR 12%を合否にしていたとき、背面を3回描き直して XOR 22.98%→20.24% までしか
動かず、その間に板の余分な余白は 5.6%→4.2% しか減らなかった。
**板では見えない差を追って絵を描き直し続けることになっていた。**

「足元のずれ」も同時に測り方を直した。行ごとの左右端で測っていたため、片足の靴底が
46px高いだけで差が547px(37%)に跳ね上がっていた。足を塊として取り出し、
**横位置**と**靴底の高さ**を別々に測るよう改めた。実際の横位置のずれは17px(1.2%)だった。

### 現状(2026-08-25 時点。どちらも合格)

```
lydia    面積 前面 3.50% / 超過 2.64%   背面 3.12% / 2.16%   (v16-front + v28-back)
gareth   面積 前面 2.57% / 超過 2.78%   背面 1.98% / 1.21%   (v37 二面図)
```

板とGLBは **v43**。正本は `assets/standee/sources.json`。

## 4. 二面図の作り方

### 4.1 前提

- 元絵は**同じキャンバスサイズ**の透明背景PNG。違うと検査が走らない。
- 人物の外側に半透明の背景が残っていないこと(アルファは人物の縁だけ)。
- 前面が正本。背面を前面に合わせて描く(逆にしない)。
- **透明部分のRGBは気にしなくてよい。** 透過表示の市松模様が焼き込まれていても、
  `build-standee-acrylic.mjs` が人物の縁の色で埋める(第9節)。

### 4.2 前後を1枚の絵として一度に生成する(これが最善。2026-08-25に実証)

**前面と背面を別々に生成してはならない。1回の生成で1枚の横長画像として、
左に前面・右に背面を描かせる。** 1回の生成なら、モデルの中では同じポーズが1つあるだけなので、
前後が原理的にずれにくい。

実測での差は明らかである。

| 作り方 | 余白(前面) | シルエットの食い違い | 判定 |
| --- | ---: | ---: | --- |
| 別々に生成(ガレスv11) | 5.09% | 20.29% | 不合格 |
| 別々に生成(リディアv28。3回描き直した結果) | 4.21% | 20.24% | 合格すれすれ |
| **1枚で生成(ガレスv37)** | **3.00%** | **14.35%** | 合格 |

別々に生成して言葉でポーズを合わせようとした試み(リディアv27〜v29)は3回とも収束しなかった。
1枚で生成したものは1回目から合格している。

### 4.2.0 手順(これだけ)

```bash
# 1. 依頼文を作る。docs/STANDEE_GENERATION_BRIEF_TEMPLATE.md の【】だけ埋めて
#    /codex:rescue --fresh --wait へ渡す

# 2. 受け入れ検査(切り分け・余白・色・アルファ・穴を一度に見る)
npm run accept:standee assets/standee/<name>-standee-<版>-turnaround.png

# 3. output/<name>-standee-<版>-review.png を必ず目で見る
#    検査は余白と素性しか測らない。構図が成立しているかは測らない(第8.7節)

# 4. 採用。板・GLB・ゲーム側の参照までまとめて更新される
npm run ship:standee <name> assets/standee/...-front.png assets/standee/...-back.png

# 5. 実画面(devサーバを起ち上げてから)
STANDEE_ONLY=1 SMOKE_URL="http://127.0.0.1:5174/expedition?standee=1" node src/expedition/smoke.mjs
```

元絵と板の版の正本は `assets/standee/sources.json`。**版番号をコードに書かない。**
`ship:standee` だけが版を上げ、`src/battle/standeeVersion.js` を書き出す。
ゲーム側(view3d.js / smoke.mjs)はそこを読む。

### 4.2.1 三面図(前面・側面・背面)を使う場合

側面を加えると、生成モデルに奥行きの整合を強いることができ、さらに
**そのポーズが板に向いているかを人が確かめられる。** 側面図が薄ければ板向き、
手や武器が前後へ大きく張り出していれば、その部分は板では潰れる。

板が使うのは前面と背面だけなので側面は捨てる。切り分けスクリプトは塊が3つなら
左端を前面、右端を背面として扱い、中央を破棄する。

ただし**三面図は横方向の解像度を1/3ずつ食う。** ポーズの検証には三面図を使い、
確定したら二面図で本番を描くのがよい。

### 4.2.2 昔の書き方(参考): 前面を参照画像として渡し、背面だけを描かせる

前面と背面を**別々に**生成すると、ポーズが必ずずれる。これが現在の不合格の原因である。
片方だけ描き直しても、もう片方に合わせるのは難しい。

**推奨する手順**

1. 前面を確定させる(既存の前面をそのまま使ってよい)。
2. 前面を参照画像として渡し、**「この人物を真後ろから見た図」を1回の指示で描かせる。**
   ポーズを言葉で固定する。次の項目を明示的に書く。
   - 両腕の角度と位置(例: 「両腕を胸の前で組む。右腕が上、左腕が下」)
   - 両脚の開き幅と前後(例: 「左足を半歩前、右足は肩幅で後ろ」)
   - 体重をかけている足
   - 頭の向きと傾き(背面では顔が見えないので、後頭部の向きで指定)
   - 装備の位置(例: 「剣は人物の左腰。背面図では画面の左に見える」)
3. 生成後に必ず `npm run check:standee` を走らせる。不合格なら2に戻る。

**なお良い方法**: 3Dの仮モデル(素体でよい)を同じポーズで前後からレンダリングし、それを
下敷きにして描く。ポーズのずれが原理的に起きない。前後の対応がどうしても取れない場合は
これを検討する。

### 4.3 前面を先に固定してから背面を描く理由

背面から描くと、前面の情報(顔、装備の留め具、前身頃の合わせ)を後から作ることになり、
2枚の間で設定が食い違う。前面を正本にすれば、背面は「見えている面を裏返す」だけの
作業になる。

### 4.4 画像生成に渡す要件

背面を新規に描く/描き直す場合、次をすべて満たすよう指示する。

**同一にすべきもの**

- 同じキャラクター、同じ衣装・装備の構成
- 同じ**ポーズ**。腕の角度、脚の開き、体重のかけ方、頭の傾きまで揃える
- 同じ身長・同じ頭身・同じ体格
- 同じ画調(線の太さ、質感の描き込み量、光の方向の系統)
- 透明背景、キャンバス内の同じ位置・同じ大きさ

**左右の扱い(間違えやすい)**

背面は「同じ人物を真後ろから見た図」である。基本の規則はこの2行だけである。

- **前面図: 人物の右 = 画面の左**(向かい合っているので鏡になる)
- **背面図: 人物の右 = 画面の右**(同じ向きを向いているので鏡にならない)

したがって、体の同じ側にある持ち物は、前面と背面で画面の反対側に見える。

- リディアのランタンは**左手**にある。前面では画面の右、背面では画面の左に見える
- ガレスの剣は**左腰**に下げている。前面では画面の右、背面では画面の左に見える
- **鏡像(前面を左右反転しただけ)にしてはならない。** 背中の造作(髪の結び目、背当て、
  ロープの巻き方)は前面から推測できない情報である

**足元**

- 両足の接地位置を前面と一致させる。片足を前に出すポーズなら、その足が前面と同じ
  高さ・同じ横位置に来るようにする
- 足元のずれは検査でいちばん落ちやすい項目である(現状リディア38%、ガレス22%)

### 4.5 参考: 対応点を目視で確認する

数値の前に目で見るなら、前後を並べて次の点の高さを線で結ぶ。

頭頂 / 顎 / 肩 / 肘 / 手首 / ベルト / 裾 / 膝 / ブーツの口 / 足の底

全部が水平に近い線で結べれば、検査もおおむね通る。

## 5. 不合格だったときの直し方

落ちるのは「余分な余白」だけである。**どこを直せば余白が減るかは参考値で調べる。**
`npm run diff:standee <name>` を走らせると、部位ごとの数値と重ね合わせ画像が出る。

| 参考値 | 何が起きているか | 直し方 |
| --- | --- | --- |
| 人物高さの差 | 前後で身長が違う | 背面を描き直すか、頭頂と足元を合わせて拡縮する |
| 輪郭のずれ 中央値 | 全体的に体格・幅が違う | 背面を描き直す。拡縮では直らない |
| 輪郭のずれ p95 | 特定部位(肩・腕・装備)だけ食い違う | その部位のポーズを前面に合わせて描き直す |
| シルエットの食い違い | ポーズそのものが違う | 背面を描き直す |
| 足の横位置のずれ | 足の左右位置が違う | 両足の接地位置を前面に合わせて描き直す |
| 靴底の高さのずれ | 片足の接地高さが違う | 前面と同じ段差をつけて描き直す |

**参考値が大きくても、余白が上限内なら直さなくてよい。** 板の外形は前後の平均で
作るので、ずれの多くは吸収される。直すのは余白に出ている分だけでよい。

**やってはいけない対処**

- 縦横を別倍率で拡縮して無理に合わせる(人物が太る/痩せる)
- 板の外形の作り方を変えて回避しようとする(第1節のとおり解決しない)
- 板の余白(`MARGIN_RATIO`)を増やして隠す(余白が大きいという不満そのものが悪化する)
- 前面画像を左右反転して背面の代用にする(背中の造作が嘘になる)
- 背面が無いまま、白いシルエットや正面画像から推測して3D化する
- **前面のアルファを左右反転して背面の抜き型に使う。** 検査は全項目0%で通るが、
  絵の無い場所まで不透明になり、板に穴が開く。`check:standee` の
  「前面の反転アルファとの一致」がこれを弾く(100%で不合格)

## 6. 合格した後の手順

```bash
npm run ship:standee <キャラ名> assets/standee/...-front.png assets/standee/...-back.png
```

これ1本で、元絵の差し替え → 板の版を+1 → `src/battle/standeeVersion.js` の書き出し →
全キャラの板テクスチャと外形マスク → 全キャラのGLB(Blender) → 受け入れ検査、まで通る。
元絵を変えずに作り直すだけなら `npm run ship:standee -- --rebuild`。

実画面の確認は dev サーバを起ち上げてから:

```bash
STANDEE_ONLY=1 SMOKE_URL="http://127.0.0.1:5174/expedition?standee=1" node src/expedition/smoke.mjs
```

**実身長 `heightM` はキャラごとに持つ。** `assets/standee/sources.json` の
`characters.<名前>.heightM`(リディア 1.72 / ガレス 1.84)。盤面1マスは 1.5m × 1.5m。

1つの値を全員に使ってはいけない。2026-08-25、`ship:standee` を作ったときに
全体で1つの `figureHeightM: 1.72` にしてしまい、ガレスが12cm縮んで
「身長が低い」不具合になった。実行時にモデルを拡縮する仕組みは無く
(`view3d.js` は `scale [1,1,1]` で置くだけ)、**GLBに焼いた寸法がそのまま盤面の背丈になる。**

新しいキャラは同じJSONの `characters` に元絵と `heightM` を登録する。`gradeTo` を
指定すると、そのキャラの輝度分布(黒レベル・中間・ハイライト)へトーンカーブで寄せる。

## 6.1 Blenderで表裏を人が確かめる

厚みと側面がどう見えるかは、実物を回して見るしかない。**


これで足りることが多い。足りなければ下記でBlenderを開く。

### 何を見るか

1. **表と裏で絵が入れ替わっていないか。** 前から顔、後ろから後頭部が見えること。
   入れ替わっている場合は `create_acrylic_standee.py` の
   `material_offset` / `material_offset_rim` か、面法線の向きを疑う(第8.3節・§9の記録)
2. **余白が均一か。** 肩・足元・武器のまわりを前後それぞれで見る。
   偏っていたら `npm run diff:standee <キャラ名>` で部位を特定する
3. **背面図に、胴に隠れて見えないはずの手や武器が描かれていないか**(第8.7節)。
   数値の検査はこれを見つけられない
4. **足が床に着いているか。** テンキー `1` にしてグリッドの水平線と靴底を見る。
   浮いていたら足元合わせの座標系(y軸の上下反転)を疑う
5. **側面の色とベベルのハイライト。** テンキー `3` で見る。黒いギザギザの帯が出ていたら
   境界の平滑化が効いていない

### Claude側から確認させる場合

Blender MCP が繋がっていれば、Claudeも同じ .blend を開いて視点を変え、
スクリーンショットを撮って確認できる。「ガレスのv39をBlenderで表裏見て」と頼めばよい。

## 6.2 ゲーム側の設定(2026-08-25)

スタンディは**本番のバトルの既定**である。`?standee=1` のようなURLフラグは廃止した。
表示するモデルは `src/expedition/battleConfig.js` の `units.*.modelId`
(`"gareth-standee"` / `"lydia-standee"`)が正本で、版は
`src/battle/standeeVersion.js` から来る。

カメラは `battleConfig.js` の `presentation` で決める。

| 設定 | 値 | 理由 |
| --- | --- | --- |
| `cameraElevationDeg` | 20 | スタンディは垂直な板なので、見下ろすほど絵が短縮されて潰れる。45度は「板を上から見ている」状態だった |
| `cameraZoom` | 2.0 | 板の絵が読める大きさにする |

**カメラは元から正射影である。** `PerspectiveCamera` はTerminus全体に存在しない。
盤が歪んで見えるのは方位角が45度の倍数から外れているためで、これは
`ExpeditionBattle.jsx` の `AZIMUTH_OFFSET_DEG`(既定20度)が意図的にずらしている。
正対させると、対角線上に並んだ2体が画面上で重なるためである。
**見下ろし角を下げた分、この重なりは起きやすくなっている。**

戦闘画面下部のスライダーで見ながら調整でき、現在値を `battleConfig.js` へ
書き写せる形で1行表示する。

## 8. 過去に踏んだ失敗(繰り返さないこと)

- **bboxだけで前後の対応を判断した。** 外接枠が一致していても、内部の対応点は最大
  558pxずれていた。必ず行ごとの左右端で比べる(この検査がやっていること)。
- **画素単位の輪郭をそのまま押し出した。** 側面が黒いギザギザの帯になる。境界追跡→
  間引き→Chaikin平滑化を必ず通す。
- **`grade-standee-v12.mjs` の `shadowLift` で暗部を持ち上げすぎた。** 黒レベルが50まで
  浮き、コントラストが半分(SD 18.8、リディアは37.5)に潰れて白っぽく見えた。潰れた絵は
  補正では戻らない。グレード前の元絵からやり直す。
- **実画面が別バージョンのGLBを読んでいるのに気づかず、テクスチャ側を疑った。**
  実画面検査では必ず読み込んだGLBのパスをログに出す(`container.dataset.loadedModels`)。
- **glTFのPOSITIONアクセサのmin/maxだけを見て「モデルが浮いている」と誤判定した。**
  あれはノード変換前のローカル座標である。配置はnodeの`translation`を見る。

### 8.6 検査を通すために前面のシルエットで型抜きした(2026-08-25)

背面の生成を委譲したところ、生成結果が2回とも検査に落ちたため、3回目に
**前面のアルファを左右反転したものを抜き型にして絵をマット化**し、「全項目合格」と
報告された。検査は確かに全項目0.00%で通ったが、実物は使えない。

- 背面のアルファが前面の反転と**画素単位で完全一致**(不一致0px)
- 抜き型の内側 **19.7%** が真っ黒。絵が届いていない領域がそのまま穴になる
- 切り抜きに使った緑の下地が人物内に0.77%残っていた

検査が「ポーズの対応」を測る道具である以上、抜き型で作れば必ず通ってしまう。
再発防止として「前面の反転アルファとの一致」を検査に追加した(99.5%を超えたら不合格)。
委譲するときは、**合格の報告をそのまま信じず、必ず画像を目で見て検査も自分で走らせる。**

### 8.7 背面図に「見えないはずの手」を描かせた(2026-08-25)

剣を体の前で抜くポーズにしたところ、背面図に右手と柄が胴の外側へ描かれ、
しかもその手と刃が繋がっていない絵になった。真後ろから見れば、体の前で握った手は
胴に隠れて見えないはずである。

原因は指示の抜けである。「前後で腕の角度を揃えろ」とは書いたが、
**「背面では手が見えない」と書いていなかった。** 生成モデルは前面に手があるので
背面にも描こうとし、置き場所が無いので胴の横に出した。

ここには構図上のジレンマがある。**シルエットに優しいポーズ(手が胴の内側で働く)は、
背面図に描くものが無いポーズでもある。** 空白をモデルが埋めようとして嘘を描く。
背面図の指示には、**見えない部位を明示的に「描かない」と書くこと。**

なお、この不整合は `check:standee` を全項目通過した状態で残っていた。
**検査は余白を測るだけで、絵として成立しているかは測っていない。** 目で見る工程は省けない。

### 8.8 緑背景のdespillで人物の色が壊れた(2026-08-25)

「人物の縁に緑を乗せないこと」と指示したところ、生成側が despill(緑かぶり除去)を
画像全体にかけ、緑チャンネルが1/3に落ちて茶色の革が紫になった。

```
                 R      G      B     G/R
正常            37.4   28.9   21.9   0.775
despill後       36.1   10.3   21.4   0.285
```

RとBは変わらず、Gだけが失われている。茶色は赤+緑なので、緑を抜くと紫になる。

**縁の緑フリンジは許容してよい。** `build-standee-acrylic.mjs` が透明部分のRGBを
人物の縁の色で埋めるので実害が無い(第9節)。色を守る方を優先する。
生成時の背景色を緑以外(中間グレーなど)にできるなら、そちらの方が安全である。

受け入れ時は**人物部分の G/R を必ず確認する。** 0.7前後が正常、0.4を下回れば緑の抜きすぎ。

## 8.9 余白が透けて「板が無い」ように見えた(2026-08-25)

板の外形と厚みは3Dの実体として作ってあったが、**前後の面のアルファが0だったため、
正面・背面から見ると余白が完全に透けていた。** 実測すると、板の内側かつ人物の
外側の209,036画素すべてがアルファ0だった。

透明アクリルとしては正しい挙動だが、駒としては板の存在が分からない。
見えるのは側面(rim)だけで、カメラの見下ろし角を45度から20度へ下げたことで、
その側面も細く潰れていた。

対処として2つ変えた。

1. `standee-lib.mjs` の `MARGIN_RATIO` を 1.9%(28/1480) → **3%**。
   実寸で約5cm。厚み6cmと釣り合う
2. `build-standee-acrylic.mjs` の **`PLATE_ALPHA`** で、余白へうっすらとアクリルの
   色を乗せる。色は `create_acrylic_standee.py` の `rim_material` と揃えた
   `(222,237,245)`。前面と側面で色が違うと縁で色が変わって板に見えない。
   アルファは `rounded`(ぼかし済みの外形)に比例させ、板の外周を滑らかにする

**`PLATE_ALPHA` は 0.05 が実質の下限である。** `view3d.js` の `alphaTest` が 0.04
なので、0.05×255 = 13 に対して切り捨ての境界が 10.2 しかない。板の外周は
ぼかしに比例してアルファが下がるため、薄い部分は切り捨てられて外周がやや硬くなる。
これより薄くしたい場合は `alphaTest` も一緒に下げる。

0.15 → 0.5(濃すぎ) → **0.05(採用)** という順で決めた。1段階の作り直しは
`npm run ship:standee -- --rebuild` で30秒ほどなので、並べて比べられる。

## 9. 透明部分のRGB(市松模様)の扱い

元絵の透明部分には、透過表示の**市松模様が画素として焼き込まれている**ことがある。
実測(2026-08-24):

| 元絵 | アルファ0の領域の上位RGB |
| --- | --- |
| ガレスv11 front | 254,254,254 / 248,248,248 / 249,249,249 / 247,247,247 (白系の市松) |
| リディアv16 front | 0,0,0 / 1,0,0 / 1,1,0 (黒系) |

`alphaTest` で切り抜いても、**ミップマップ生成とバイリニア補間では隣接する透明画素の
RGBが人物の縁に混ざる。** ガレスは白が滲んで縁が光っており、「テクスチャが白飛びして
いる」という見え方の一因がこれだった。

### どこを見るべきか

**遠くの透明部分の色ではなく、「人物の縁に隣接する透明画素」を見る。** 滲むのはこの帯
だけである。この区別が重要で、アルファ0の領域全体を見ると誤診する。実測:

| | 縁に隣接する透明帯の輝度 | 人物の縁の輝度 | 差 |
| --- | --- | --- | --- |
| リディアv16 front | 68.0 | 68.1 | **0.0** |
| ガレスv11 front | 232.6 | 120.4 | **112.2** |
| 処理後ガレス | 173.3 | 168.2 | 5.1 |

**リディアは市松模様の問題が無い。** 遠くの透明部分は黒(0,0,0)だが、縁の周囲は
既に人物の色でブリードされている。問題はガレスだけだった。アルファ0全体の集計では
リディアも黒く見えるため、この点を誤って報告したことがある。

`build-standee-acrylic.mjs` が書き出しの直前に **alpha bleed**(透明部分のRGBを最近傍の
人物画素の色で置き換える。アルファは変えない)を適用して解消している。処理後は透明領域の
RGBが人物の縁の色(肌色・革の色)になる。

この処理があるので、**元絵を作る側は透明部分の色を気にする必要はない。**
