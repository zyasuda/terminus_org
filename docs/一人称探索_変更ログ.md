## 2026-08-31 実機で1周遊んだ後の指摘4件を直した

作者の指摘: (2)線画3Dがうそくさい・壁や間仕切りが不正確 (3)自分の向きが分からない(地図でも同じ)
(4)後退が無い (5)灯りと奥の暗闇の演出が欲しい

### (2) 描画をマス単位のpainter's algorithmに作り直した

**2回失敗している。経緯を残す。**

1. 最初の実装は「前進できるマスの列」を四隅で結ぶだけで、左右を一度も見ていなかった。
2. 次に左右の開閉を見て壁/開口を描き分けたが、**正面1列しか持っていなかった**。
   横は「壁まで何マスか(leftRun/rightRun)」という近似で、視界の外側のマスは存在しなかった。
   部屋の角や横穴が表せず、地図と食い違って見えた。

3回目でgrid-based dungeon crawlerの定石に合わせた(Dungeons of Noudar 3D の解説、
rpgcodexの「Wizardry系はどう描いているか」の議論):

1. **カメラ前方のマスを格子として取り出す**(`mapwalk.js`の`viewCells`)。
   u = 横(右が正)、d = 奥行き(0が足元)。1列ではなく面で持つ。
2. **壁のマスを遠い順に描く**(painter's algorithm)。手前の面が奥を塗りつぶすので、
   隠面の計算はいらない。overdrawは出るが、この規模では問題にならない。
3. **隣のマスを見て、隠れる面は描かない**。
   - こちらを向いた面 = 手前のマス(u, d-1)が開いている時だけ
   - 左の側面 = そのマスが画面の右側(u > 0)にあり、左隣(u-1, d)が開いている時だけ
   - 右の側面 = その鏡像。正面(u = 0)の壁は側面が見えない
4. 壁の向こうの床と敵影は`hasLineOfSight`(Bresenham)で落とす。
   壁そのものは上書きで隠れるので、視線判定は「見えるかどうか」だけに使う。

**壁は不透明でなければならない。** 一度、遠近感を`opacity`で付けて奥が透けた。
壁は`opacity`を持たず、背景色(FOG)へ寄せた**色**で遠近を表す(`shade()`)。
painter's algorithmは「手前が奥を塗りつぶす」ことが前提なので、半透明の面を混ぜると成立しない。

投影は1本の式だけ。目は足元のマスの中心にあり、マスdの手前の境目までの距離は d - 0.5 マス。

```
sx(u, t) = CX + u * FOCAL / max(t, NEAR_CLIP)
sy(h, t) = CY + h * FOCAL / max(t, NEAR_CLIP)
face(uA,tA,uB,tB)  // 天井から床まで届く1枚の面
```

壁の正面・側面・床の目盛り・敵影が、全部この`face`と`sx/sy`で置ける。

**画面の縦横比**: 戦闘盤に合わせると通路は幅4.5m×高さ3mの低く広い断面になる。
縦長の枠だと床と天井の余白ばかりになるので、窓を横長(300×250)にした。

### (3) 向きの表示

- 地図: 現在地の丸を**向きの三角**に変えた(`RogueMap.jsx`の`FACING_ANGLE`、`.rogue-player-arrow`)。
  地図の見出しに「↑北 / 現在の向き: 東」を出し、地図の北が画面上であることを明示。

### (4) 後退

`core.js`に`back(floor)`を追加。`mapwalk.js`の`opposite(facing)`へ1歩下がり、**向きは変えない**。
通路の自動通過は前進と同じ扱い。UIは前進ボタンの下の「後退」ボタンと`↓`キー。
後退でも固定敵への接触判定(`hallContact`)を通す。

### (5) 灯りと暗闇

- 断面の深さで線の濃さを落とす(`fade(depth)`: 奥ほど薄い)。
- 手前を暖色で照らす放射グラデーション(`fp-lamp`, screen合成)。
- 周辺を闇へ落とすビネット(`fp-vignette`)。

  傾きを戻したい場合は`.rogue-map`の`perspective`と`.rogue-map svg`の`transform`を戻す(2行)。

### 床と天井を戦闘盤に合わせた(2026-08-31 追加修正)

**換算**: 戦闘の通路盤は `width 7 × height 3`(`battleConfig.js`)で、**通路の幅は3マス**。
探索の通路は1マス幅なので、**探索1マス = 戦闘3タイル**。`FirstPersonView.jsx`の`TILES_PER_CELL = 3`。

- **床**: 戦闘と同じ1タイルきざみで目盛りを引く。探索1マスの中に3本入る。
  マス境界の線を濃く、タイル境界を薄くしてある。左右3マスで打ち切り(見た目の都合、判定とは無関係)。
- **天井**: 戦闘3Dの入口アーチ `view3d.js` の `ARCH_HEIGHT_TILES = 2.0`
  (コメントに「1マス1.5m換算で3m」)を指標にした。目の高さはアーチのコメント
  「人の約1.6倍」から逆算した背丈(2.0/1.6 = 1.25タイル)のやや下として`EYE_TILES = 1.15`。
  結果、通路は**幅4.5m × 高さ3m**の低く広い断面になる。低いと感じたら`CEIL_TILES`だけを上げる。
- 敵影の背丈も戦闘Configの見かけの高さ(0.9タイル)に合わせた。

`core.test.mjs`に`corridor.height === 3`の検査を置いた。戦闘の通路幅を変えたらここで落ちるので、
床の刻みも一緒に直すこと。

### 戦闘中の離脱「入口へ戻る」(2026-08-31 追加)

戦闘画面に離脱ボタンを足した。`onFinish("escape", 現在HP)`を投げ、
`ExpeditionView.finishBattle`が`core.js`の`retreatToEntrance`で入口へ戻す。

- **敵は倒した扱いにしない**。`events`も`hallDefeated`も触らないので、戻ればまた戦える。

### 地図に間仕切りが無かった(2026-08-31 追加修正)

作者の指摘「右に壁はない」。実測したところ**一人称が正しく、地図が間違っていた**。

`draw.js`の`roomShapes`は部屋を**角丸長方形1枚**で描く。大広間の間仕切りは`interior.js`が持つ
別の壁集合なので、地図にだけ描かれていなかった。探索の当たり判定にも戦闘盤面にも壁があるのに、
地図では素通しの大部屋に見える。

再現: seed 1448944938 の大広間で、開口の1マス西(-14,3)から東を向く。
右(南)は間仕切り、正面と左は開口。一人称はその通りに描く。地図には何も無かった。

直し: `interior.js`に`hallWallCells(map)`を足し、`RogueMap`がそれを塗る。
隣のマスを見たことがある壁だけ出す(壁は隣に立って初めて分かる)。
検査は「地図が描く壁は必ず通れない」「通れない壁は必ず地図に出る」の双方向で置いた。

**部屋を1枚の形で描いている限り、部屋の中に足した壁は必ず地図から落ちる。**
今後 interior.js に内装を足したら、`hallWallCells`相当を地図へ出すところまでが1つの作業。

## 2026-08-31 一人称をthree.jsの3Dにした(SVG版は残してある)

作者の判断: 「一人称はThree.jsで3Dで描いた方が早いのでは」。その通りだった。

**理由はバグの数ではない。** 戦闘側には既に段差・法面・瓦礫9種・入口アーチのモデルがある
(`view3d.js`)。方針の核が「探索で見た地形をそのまま戦闘へ引き継ぐ」である以上、
探索がSVGのままだと**同じ地形を2回実装する**ことになる。壁しかない今は気づかないが、
机や柱を置いた瞬間に破綻する。

`createBattleScene`は再利用していない。1900行の単一クロージャで、カメラ操作・スタンディ・
d20演出が絡んでいる。読んだのは「グリッド→箱」の作り方だけで、一人称用に別の小さいシーンを書いた。

- `src/expedition/firstPersonScene.js` — three.jsのシーン(約110行)。
  座標系は戦闘と同じ**1単位=1タイル**。探索の1マス=3タイルなので`CELL = 3`。
  壁は「空きマスに隣り合う、通れないマス」だけ箱にする。地図の外を無限に作らない。
  地図が変わった時だけ組み、1歩ごとには作り直さない。常時ループも回さない(1入力=1描画)。
- `src/expedition/FirstPerson3D.jsx` — SVG版と操作もHUDも同じ。描画だけ差し替え。
- 灯りは`PointLight`。`distance`が「灯りの届く範囲」の正本になる。霧は`THREE.Fog`。
  SVGでは`fade()`と放射グラデーションで手作りしていたもの。
- 高DPRの`setPixelRatio`上限2は、戦闘で踏んだ事故(canvasが2倍にはみ出す)への同じ対策。
- `dispose()`でジオメトリ・マテリアル・rendererを解放する。探索⇄戦闘でWebGLの文脈が2つになるため。

**GPUに任せて消えたもの**: 自前の投影、painter's algorithmの並べ替え、隣接マスの隠面判定、
壁越しの視線判定。SVG版に残っているが、3D版はどれも持たない。

**壁の正本は変わっていない**。3DもSVGも`isOpen`/`hallBlocked`を読む。地図も同じ。

### SVG版は削除した(2026-08-31)

見比べた結果、作者が3Dを採用。`FirstPersonView.jsx`と切り替えUIを消し、
自前の投影・painter's algorithm・隣接マスの隠面判定・壁越しの視線判定(`viewCells` /
`hasLineOfSight`)も一緒に消した。GPUがやることを二重に持たない。

代わりに`mapwalk.js`へ`levelCells(map)`を置いた。「通れるマス」と「壁として立てるマス」に
分けるだけの純関数で、3Dのシーンが読む唯一の入口。描画に依存しないのでNodeで検査できる。

### 歩行と旋回の補間、カメラの向き

- 1マスを190ms、90度を170msで詰める。**動いている間だけrAFを回し、着いたら止める**
  (常時ループにしない。電池と発熱)。初回だけ補間せずその場に置く。
- 向きは`mapwalk.js`の`FACING_YAW`が正本。**three.jsのカメラは`rotation.y = 0`で -Z を向く**。
  地図の北を -Z に取ったので north が 0。ここを一度ずらして地図と180度食い違わせた。
  `FACING_YAW`と`FACING_AHEAD`が一致することをNodeで検査している(three.js不要)。
- 旋回は目標角を現在角から±πへ畳む。北⇄西で遠回りしない。
- **カンテラ(松明)**: 見た目の正本は`src/battle/lanternLook.js`。色・強さ・距離減衰・
  炎の揺らぎ(4つのsinの重ね合わせ)・揺らぎの速さを、戦闘と探索が同じものを読む。
  色`0xffe3bd`は`scripts/lantern-tune.mjs`で床の無彩色からの偏りを実測して決めた値
  (26.4%→3.3%)。**勘で変えないこと。** 変えるならスクリプトで測り直す。
  距離減衰は必ず0。既定の逆二乗だと光源のすぐ隣だけが白飛びする。
  射程だけは場面で違う: 戦闘は3タイル、探索は`LANTERN_RANGE_CELLS`(1.6マス)分。
  一人称は進行方向の奥まで見えるので、3タイルだと1マス先から真っ暗になる。
- **床の橙は取り切れていない(未決、2026-08-31)**: 探索の床を同じ指標で測ると偏り**28.4%**。
  中立色の補助光を足しても取れなかった(環境光0.34+key0.36で16.3%、環境光0.55単独で16.2%)。
  理由は framing の違い: 戦闘のカメラは盤を見下ろすので床の大半がカンテラの射程の外にあり、
  中立の環境光で照らされている。一人称は**常に射程の中にいる**ので、床の色をカンテラが決める。
  「グレーの石」と「戦闘と同じカンテラ」は一人称では両立しない。作者の判断待ち。
- **入口アーチ**: 部屋と通路の境目(`kind`が`corridor`かどうかが変わる隣り合わせ)に、
  戦闘の書き割りと同じ寸法(幅1.4 × 高さ2.0タイル)で線を引く。
  **高さの物差しとして置いた。** 通路の高さ = アーチの高さ = 2.0 なので、
  アーチの頂点が天井とぴったり一致する。作者が「壁が低い」と感じた理由はこれ。
  **決着(2026-08-31)**: 作者が実機のスライダーで**天井2.5タイル(3.75m)**に決めた。
  出入口と坑道の高さは別のものなので、正本を2つに分けた。
  - `DOORWAY_HEIGHT_TILES = 2.0` — 人が通る出入口。戦闘の書き割りの入口アーチと、探索のアーチ
  - `PASSAGE_HEIGHT_TILES = 2.5` — 坑道の天井。探索の一人称だけが読む
  スライダーは残してある(まだ触るかもしれないため)。確定したらスライダーごと消す。
- **味方の駒(リディア・ガレス)**: 戦闘と同じスタンディを、パーティのマスの中心から
  「横」と「前」(タイル)でずらして置く(`PARTY`配列)。2人とも視界の左を歩く。
  **横は通路の半分(1.5タイル)から板の幅の半分(約0.45)を引いた範囲に収めること。**
  越えると壁を突き抜ける。
  カメラは中心より`CAM_BACK`分だけ後ろにいるので、背中が視界の左に入る。
  材質は戦闘と同じMeshBasicMaterial + アルファ抜き(光源で照らすと濃い衣装だけ白飛びする)。
  スタンディは+Zが正面なので、進行方向へ向けるには`yaw + π`。
  モデルが読めなくても探索は続く(同行者が出ないだけ)。
- **駒の実寸(2026-08-31に実測)**: `battleConfig`の`units[].height`(1.6)は**駒の実寸ではない**。
  `view3d.js`ではカンテラを提げる高さと、モデル読み込み前の仮の箱にしか使っていない。
  GLBは等倍で置かれるので、実寸はGLBが決める。実測: リディア**1.209**、ガレス1.303、
  坑道の獣0.569タイル。アーチ(2.0)はリディアの1.65倍で、コメントの「人の約1.6倍」通り。
  作者が「リディアの3倍に見える」と指摘した壁は`BACKDROP_H`(3.6 = リディアの2.98倍)。
  盤の外を塞ぐ書き割りで、通路の壁ではない。高さを直すかは未決。
- **通路の高さ**: `stoneLook.js`の`PASSAGE_HEIGHT_TILES`(2.0タイル = 1マス1.5m換算で3m)。
  戦闘の入口アーチ(`ARCH_HEIGHT_TILES`)と探索の天井(`CEIL`)が同じものを読む。
  **戦闘の`WALL_H`(1.0)とは別物。** あちらは「見下ろした時に駒が隠れない高さ」で決めた
  盤上のブロックの高さで、通路の高さではない。探索でWALL_Hを使うと天井が目の高さ(1.15)より
  低くなり、歩けない絵になる。
- **床の石**: 見た目の正本は`src/battle/stoneLook.js`。塵と同じく戦闘と探索が同じものを読む。
  テクスチャ1枚 = 3タイル = 探索のちょうど1マスなので、探索側は既定のUVで貼れる。
  **壁と天井には貼らない**。戦闘の壁は無地(`COLOR.wall`)なので、探索だけ石を貼ると食い違う。
  稜線と床の目盛りはそのまま残してある(マスの区切りは遊びの情報なので消さない)。
- **塵**: 見た目の正本は`src/battle/dustLook.js`。**戦闘と探索が同じものを読む**。
  一度これを分けて作り、作者に「バトル画面の塵と違う」と指摘された。戦闘の塵は
  *上へゆっくり立ち上り*、粒ごとに大きさが違い、加算合成で薄い。落ちる均一な点ではない。
  `PointsMaterial`は全粒子が同じ大きさになるので、粒ごとに変えるためSpriteを使う。
  ここで決めるのは**どこに何個置くか**だけ: 戦闘は7×3の盤に22個。同じ密度になるよう、
  探索はカメラの周り±1マス(=±3タイル)に38個。外へ出たら反対側へ回り込ませるので、
  歩くと塵が後ろへ流れて視差が出る。地図全体へは撒かない。
  **塵を入れたのでrAFは回り続ける**(止まっていても舞うため)。
  代わりに`visibilitychange`でタブが隠れたら止め、戻ったら再開する。
- **カメラの引き**: 立ち位置から後ろへ`CAM_BACK_DEFAULT`(2026-08-31時点で0.60タイル。作者が実機で決めた)。

### 地図と一人称の整合を検査で固定し、戦闘のアーチも地図から読むようにした(2026-09-01)

作者の指示: 「Rogue Map、一人称画面、戦闘画面の整合性をどう取るかが問題なので、
優先順位として、Rogue Mapと一人称画面の整合性を先に固める必要がある」。

#### 1. 地図 ⇄ 一人称(土台)

地図(`draw.js`)は模式図で、部屋を角丸長方形(0.06マス内側)、通路を中心線のストローク
(線幅0.62マス)で描く。**寸法の正本ではない。** だから「形が同じか」ではなく
「歩ける場所と塞がれた場所が同じか」で揃える。

    地図が床として塗る集合 = 部屋の全セル + 通路の経路セル − 間仕切り
    一人称が歩ける集合     = levelCells(map).open

実測: 60 seed・**18,646セルで食い違い0**。`core.test.mjs` に常設。
地図が間仕切りを描かなかった頃(実際にあったバグ)を再現すると480件で落ちる。

#### 2. 戦闘のアーチ(私が入れた回帰の修正)

作者の指摘「現状の壁一枚の幅は3マスだよね。矛盾してるのでは？」から発覚。

戦闘は開口部を**盤の縁**から作っていた(`view3d.js`)。三叉路は枝の先だけが縁なので
合っていたが、通路戦の盤を部屋の実寸から組むようにした(3fcdc6d)ら盤が全面床の長方形になり、
**外周ぜんぶが縁**になった。同時に `voidBoundaryWalls` の条件が
`typeof layout === "object"` に変わり、以前は無効だったこの処理が有効になっていた。

実測: 戦闘部屋80件すべてで**実際の出入口は2本**なのに、四辺に4枚のアーチが立っていた。
壁1枚の幅が3マスに見えたのは、部屋の一辺まるごとを1枚の壁として塗っていたため。

直し方: `core.js` に `roomDoorways(map, room)` を足し、通路の端点に隣接する部屋のセルを
出入口として読む。`board.openings` として戦闘へ渡し、`createBattleScene` の
`openings` に載せる。**渡された辺だけがアーチになり、残りの外周は普通の壁**になる。
渡さない盤(三叉路)は従来どおり縁ぜんぶを出入口にする。

`door.direction` は「部屋aから見た向き」でbの側では逆になるため、方向名は使わず
「通路の端点の隣が部屋か」で決めている。両側から同じ答えが出る。

実機(4×3の盤): 開口部14 → **1**、盤外の壁 0 → **13**。外周の辺は 2w+2h = 14 で辻褄が合う。

検査: `seed 1〜40 × fight-0/fight-1` で「盤の出入口 == 地図の出入口」「出入口の数 ==
接続している通路の本数」「出入口は部屋の縁」「出入口の外は通路」。
出入口を渡さないように壊すと `seed 1 fight-0: 盤の出入口は地図から読む` で落ちる。

**大広間の見た目も変わる。** 以前は外周4辺(16,12,12,16タイル)にアーチが立っていたが、
出入口1本ぶんだけになる。

### 縮尺のループを止めた ─ CELLは見せ方の倍率であって寸法ではない(2026-09-01)

作者の決定:

> アーチ壁の幅は3マスありますが、それは無視して1マスと扱うのはどうでしょうか？

これで決着。**正本は「マス」の側にある。** どのマスが歩けるか、どの境目に出入口があるかが
唯一の事実で、戦闘盤はそれを1マス=1タイルで組む。一人称が1マスを画面上で何単位の幅に
描くかは**絵の話**で、寸法ではない。地図(`draw.js`)が部屋を角丸長方形、通路を線幅0.62マスの
ストロークで描く模式図なのと同じ立場。

- `CELL = 3` に戻した。1にすると縦長のスリットになり、ゲームとして成立しない(作者の判断)。
- **`CELL` を export しない。** 外へ出すと「探索1マスは戦闘の3タイル」という誤った換算が
  生まれる。2026-08-31に私(Claude)が実際にそれをやり、三叉路の戦闘盤の枝を3タイル幅で
  組むところまで波及させた。Codexも同じところでループした。
- `core.test.mjs` に見張りを入れた。`firstPersonScene.js` 以外のファイルが `CELL` を
  含んでいたら落ちる。`export const CELL` に戻しても落ちる(壊して確認済み)。

タイル単位へ直した値(霧2.4/12.6、塵±3、床の石 repeat=CELL/3、敵印0.66、カメラ遠方36)は、
CELL=3では以前と同じ値になる。見た目は変わらない。

#### これで残る食い違い

三叉路の盤の枝が3タイル幅なのは、**もう食い違いではない。** 枝は通路1マスぶんで、
盤の上で3タイルの幅を取っているだけ。戦闘に陣取りの余地を持たせるための描き方であって、
通路が3マス幅だという主張ではない。同じ理由で一人称のアーチ壁も画面上3マスぶんの幅で描く。

残るのは壁の高さ(戦闘の書き割り3.6 / 一人称の天井2.5)だけ。これも見せ方の値なので、
揃える必要があるかどうかから決める。
