## 第1部: 調べられるものに前提条件を付ける

### 1.1 データ

`secret.requires` を、**行き先と同じ語彙**で持たせる。

```js
{ id:"s5b", entity:"人型", aliases:["人型"], requires:{ secretsAll:["s5a"] }, ... }
```

`secretsAll` / `secretsAny` の両方に対応する（`requiresMet` がそのまま扱える）。**新しい語彙を作らない。**

### 1.2 エンジン（`src/gamebook.js` のみ変更）

`progression.js` は触らない。塞ぐのは `gamebook.js` 側で行う。

**(a) 選択肢から消す** — `candidates()`（`src/gamebook.js:115` 付近）が `actionCandidates()` の結果を受け取っている。そのうち `id` が `secret:` で始まるものについて、対応する秘密の `requires` が満たされていなければ**取り除く**。

**(b) 調べられなくする** — `act()` の調査の分岐（`src/gamebook.js:173` 付近、`pickExamineSecret` を呼んでいる箇所）で、返ってきた秘密の `requires` が満たされていなければ、**その秘密は見つからなかったものとして扱う**（`secret` が無いときと同じ経路＝出口の解決へ進み、最終的に `unknown` になる）。

判定は `requiresMet(secret.requires, state)` を使う。`progression.js` から import する（既に export されている）。

**満たされていない秘密を、別の秘密として誤って開かせないこと。** `pickExamineSecret` の戻り値をそのまま使わず、条件を満たさなければ「見つからなかった」に倒す。

### 1.3 エディタ（`src/editor.js` の `secretEditor`）

入力欄を2つ足す。**既存の `exitEditor` の「必要な発見」と同じ形にすること**（`select multiple` ＋ `data-field="secretsAll"` の扱い）。新しい入力の仕組みを作らない。

- **「調べる前に必要な発見」** — 同じ場面の他の秘密から複数選ぶ。**自分自身は選択肢に出さないこと**
- **「調べると手に入る物」** — 文字列1つ。`node.loot` に `{ name, requires:<この秘密のid> }` として書く。空にしたら該当の `loot` を取り除く

`loot` は秘密の中ではなく場面の直下にある。**この対応付けを `update()` で正しく行うこと。** 提案の仮編集中（`pendingProposal` があるとき）は章データに書き込まないという既存の原則を守る。

### 1.4 検査（`src/validate.js`）

`structureFor` に1件足す。

- 秘密の `requires.secretsAll` / `secretsAny` が**存在しない秘密のidを指している** → `error`、メッセージ `必要な発見が存在しない`、場所は `sceneLabel(where)`

## 第2部: 流れを図として見せる

### 2.1 置き場所

`nodeEditor()` の中、**シナリオ補完のパネルの下・入力欄（`#author-form`）の上**に `<section id="chain">` として置く。見出しは `<h2>この場面の流れ</h2>`。

**入力欄ではない。読むためのもの。** ボタンを置かない。

流れが1本も無ければ、**見出しごと出さない**。

### 2.2 何を描くか

その場面から始まる連鎖を、字下げした木として描く。

```
封鎖の木柵 を調べる                          44回
   └ 錆喰い が現れる
        └ 倒すと 抜け道 が現れる             44回
             └ 右へ進む が選べるようになる
崩れた坑道 を調べる                          38回
   └ 坑道蝙蝠 が現れる
        └ 倒すと 壊れた機械人形 が現れる      33回
油の匂い を調べる                            41回
```

**根**: その場面の秘密のうち、`requires` が無く、かつ `trigger` か `aliases` を持つもの（＝最初から調べられるもの）。

**秘密から伸びる枝**（この順で）:

1. `node.loot` に `requires === その秘密のid` のものがあれば → `└ 調べると <物の名前> を手に入れる`
2. 同じ場面の秘密で `requires.secretsAll`/`secretsAny` にその秘密のidを含むもの → `└ <要素名> が現れる`（そこから再帰）
3. 同じ場面の遭遇で `requiredElements` にその秘密の `entity` または `aliases` のどれかを含むもの → `└ <敵の名前> が現れる`（そこから再帰）
4. 同じ場面の行き先で `requires.secretsAll`/`secretsAny` にその秘密のidを含むもの → `└ <進むときの言葉の1つ目> が選べるようになる`

**遭遇から伸びる枝**:

- `enemy.revealOnDefeat` が指す秘密 → `└ 倒すと <要素名> が現れる`（そこから再帰）

**深さの上限は5。** 同じ節を1本の枝の中で2度たどらないこと（循環しているデータでも止まること）。

**内部のidを一切出さないこと。** 出すのは要素名・敵の名前・物の名前・進むときの言葉だけ。

### 2.3 回数を添える

秘密の節の右に「その秘密が自動プレイ50回のうち何回開いたか」を出す。**0回なら `0回` と出す**（作ったのに誰も通っていないことが分かる）。

そのために `src/validate.js` の `play()` に集計を足す。各runの終了時に `state.revealed`（`Set`）の中身を数え、`result.reveals` を `{ <秘密のid>: <回数> }` の形で返す。

エディタ側は `paintInspection()` が既に `inspect()` を呼んでいる。**`inspect()` の呼び出し回数を増やさないこと。** 直近の結果を保持して図の描画に使うこと（`paintInspection` が受け取っている `result` を使い回してよい）。**図のために `inspect()` を追加で呼ばない。**

回数が無い節（遭遇・行き先・物）には回数を出さない。

### 2.4 見た目

`editor.html` にCSSを足す。既存のトークン（`--flame` / `--heart` / `--dim` / `--ash`）だけを使う。新しい色を導入しない。

- 字下げは `padding-left` で行う。表や罫線を使わない
- 回数は `--dim`。**0回のときだけ `--rust`**
- 等幅にしない（本文と同じ `--mech`）
