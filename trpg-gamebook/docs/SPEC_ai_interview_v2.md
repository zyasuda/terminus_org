## 最優先の原則（v1と同じ、繰り返す）

作者が気持ちよく物語作りに集中できること。内部ID・条件式を見せない。作者の文章を承認なしに書き換えない。待ち時間を無言にしない。AIが落ちても書く作業は止まらない。一度に1つずつ聞く。正しさは機械（`inspect()`）が見る。**加えて、返事に評価語・感想を含めない**（v1 §3‴で確定済み）。

## 1. 話題を4つに分け、タブで切り替える

現在、パネルは常に「調べられるもの」だけを話している。これを、**同じ1つのパネルの中でタブを切り替える**形にする。

```
┌─────────────────────────────────────┐
│ シナリオ補完              Gemini設定  │
│ [調べられるもの] 行き先  決断  遭遇     │  ← タブ
│                                       │
│ （選んだ話題の会話がここに表示される）    │
└─────────────────────────────────────┘
```

- 会話・提案は**話題ごとに別々に保持する**。既存の `talks`（`Map`、キーは `selected.node`）を、キーを `${selected.node}:${category}` に変える
- 話題を切り替えても、それぞれの会話は消えない（タブを戻せば続きが見える）
- 各タブの最初のAIの問いかけは話題に応じて変える（§3参照）

## 2. なぜ行き先・決断・遭遇が難しいか

「調べられるもの」は自己完結したデータ（要素名・呼び名・本文）だったので、AIが作ったものをそのまま採用できた。**行き先・決断・遭遇は、他のデータを参照する。**

| 話題 | 参照するもの | 存在しないものを書かせると起きること |
|---|---|---|
| 行き先 | 実在する場面・エンディング | `to` が存在しないシーンを指し、今日見つけた欠陥（§21〜22参照）と同じ壊れ方をする |
| 決断 | その場面の調査・遭遇・出口の言葉 | `choices[].input` が何にも解決できず、黙って何も起きない（§18で見つけた不整合と同じ） |
| 遭遇 | その場面の秘密（`requiredElements`・`revealOnDefeat`） | 存在しない要素名・IDを指し、遭遇が発火しない、または撃破後に何も開示されない |

**対策**: AIに実データの一覧をプロンプトで渡し、**その一覧の中からそのまま選ぶ**ように指示する。返ってきた値が一覧に無ければ、**その項目だけ空のまま**にして、既存のフォーム（`exitEditor` / `decisionEditor` / `encounterEditor`）で作者に選ばせる。黒く塗って誤魔化さず、空欄として渡す。

## 3. 話題ごとの仕様

### 3.1 行き先（`exits`）

**AIに渡す一覧**: `nodes()` から、イントロと現在の場面を除いた場面名・エンディングの一覧（既存の `exitEditor` の `options` と同じ集合）。

**AIへの指示**: 「作者の描写から、この場面がどこへ通じるかを聞く。行き先は必ず与えられた一覧から選ぶ。一覧に無い行き先は作らない」

**提案の形**:
```json
{"proposals":[{"toLabel":"灯りの部屋","match":["右","坑道の奥"],"text":"到着時の一文","blockedText":"進めないときの一文"}]}
```

**採用時の解決**: `toLabel` が一覧の場面名と**完全一致**すれば `to` をその場面のidへ解決する。一致しなければ `to` を未設定のままカードを採用し、`exitEditor` を開いた状態にして作者に選ばせる（エラーにしない。空欄も正しい状態として許容する）。

`requires.secretsAll` はAIに提案させない（v1でも同様に扱わなかった判断を維持する。任意の追加要件なので、必要なら作者が手動で足す）。

### 3.2 遭遇（`encounters`）

**AIに渡す一覧**: 現在の場面の `secrets[]` の `id` と `entity`（`requiredElements` はentity/aliasesの文字列一致で判定されるため、entityの一覧を渡せば十分）。

**AIへの指示**: 「作者の描写から、この場面に潜む敵と、それが発火する条件を聞く。`requiredElements` は与えられた要素名からそのまま選ぶ。無ければ空にする。撃破後に何が分かるか（`revealOnDefeat`）も、与えられた秘密のidから選ぶ。無ければ空にする」

**提案の形**:
```json
{"proposals":[{"triggerTerms":["奥へ進む","右へ進む"],"requiredElements":["封鎖の木柵"],"onsetText":"何かが動いた気配がした","enemyName":"名前","enemyHp":6,"revealOnDefeatLabel":"抜け道"}]}
```

**採用時の解決**: `requiredElements` は渡した一覧に無い値を除く（黙って削る。全部除かれて空配列になってもよい＝無条件で発火する遭遇になる）。`revealOnDefeatLabel` は渡した秘密の `entity` と完全一致すれば対応する `id` を `enemy.revealOnDefeat` に入れる。一致しなければ空のまま。

### 3.3 重要な決断（`decision`）

**この場面には既に決断がある場合、AIに提案させない。** タブを開いたら「この場面には既に決断があります」と出し、既存の `decisionEditor` を見るよう案内する（1場面1決断という既存の制約を守る。上書きしない）。

決断が無い場合のみ、取材を行う。

**AIに渡す一覧**: 既存の `decisionEditor` の `suggestionGroups` と全く同じもの（調べる: `${entity}を調べる`、遭遇: `triggerTerms`、行き先: `match`）。重複を除き最大6件ずつ、というルールも同じにする。**新しい一覧の作り方を増やさない。既存の関数から作る。**

**AIへの指示**: 「作者の描写から、プレイヤーが迫られる葛藤（安全と時間、情報と危険、誰を信じるか）を聞く。選択肢は2つ。それぞれの`input`は、与えられた一覧の言葉から**そのまま**選ぶ。一覧に無い言葉は作らない」

**提案の形**:
```json
{"proposals":[{"prompt":"金属音が近づいている。安全を確かめるか、隙間を急ぐか。","choices":[{"label":"木柵を調べ、安全な通路を探す","input":"封鎖の木柵を調べる"},{"label":"崩れた坑道を急いで進む","input":"崩れた坑道を調べる"}]}]}
```

**採用時の検証**: 採用前に、各 `choices[].input` を `decisionInputResolves(node, input)` で確認する。**1つでも解決できなければ、そのカードは採用ボタンを無効にし**、「解決できない選択肢があります」と表示する。既存の `decisionEditor` を開いて手動で直させる（この検証経路は新しく作らず、既存の `decisionInputResolves` を呼ぶだけ）。

### 3.4 調べられるもの（既存、変更しない）

v1のまま。

## 4. `src/ai.js` の変更

`systemInstruction`（固定の1本）を、**話題ごとの指示を返す関数**に変える。

```js
export function systemInstructionFor(category, context)
// category: "secrets" | "exits" | "decision" | "encounters"
// context: { destinations?: [{label}], secrets?: [{id,entity}], suggestionGroups?: [[label, values[]]] }
```

- 各指示文の末尾には、v1 §3‴で確定した「評価語・感想を書かない」の一文を**共通で**含める（4つとも同じ文言を使い、コピーではなく1つの定数を組み込む）
- 一覧（`destinations` / `secrets` / `suggestionGroups`）は、指示文の中に埋め込んで渡す。「次の一覧からそのまま選ぶこと」という指示と一緒に

`ask()` の引数に `category` を追加する。`parseReply` は**話題を区別しない**（プロパティ名が話題ごとに違うだけで、パースの形＝```json ブロックを取り出す部分は共通のロジックのまま）。**例外を投げない原則は全話題で維持する。**

## 5. `src/editor.js` の変更

- タブUIの追加（§1）
- `talkFor` / `setTalk` のキーを `${selected.node}:${category}` に変える。現在選んでいるタブを保持する状態（`selected.aiCategory` 等）を追加する
- 各話題の最初の問いかけ文を変える:
  - 調べられるもの（既存）: 「この場面には、何がありますか。見えるもの、匂い、音、気配。思いつくまま書いてください。」
  - 行き先: 「この場面は、どこへ通じていますか。」
  - 遭遇: 「この場面に、危険はありますか。」
  - 決断（決断が無い場合のみ）: 「この場面で、プレイヤーは何かを選ばなければなりませんか。」
- 話題ごとの `adoptProposal` を追加する。既存の `secretId()` のようなID生成規則を使い、`exits` は `newId("exit_", ...)`、`encounters` は `newId("encounter_", ...)` を**既存の `add()` 関数と同じ規則で**流用する（新しい採番規則を作らない）
- 提案カードの見た目（§4のフィールドの表示）は、話題ごとに表示する項目が変わる。既存の「採用／直す／捨てる」の型は維持する
- 「直す」を押すと、その話題の既存編集画面（`exitEditor` / `decisionEditor` / `encounterEditor`）が、提案の内容を仮に入れた状態で開く。**v1の`pendingSecret`と同じ仕組みを、話題ごとに一般化する**（`pendingSecret` を `pendingProposal = {category, data}` のような形にまとめてよい）

## 6. 検査（`test/ai.test.mjs` への追加）

既存4件は残す。次を追加する。**通信しない。**

1. 行き先の提案で `toLabel` が一覧に一致しない場合、採用後の章データの `to` が未設定のままであること（存在しない値を書き込まない）
2. 遭遇の提案で `requiredElements` に一覧に無い値が混じっている場合、採用後はその値が除かれていること
3. 決断の提案で `choices[].input` が解決不能な場合、採用できない（採用処理を呼んでも章データに書き込まれない）こと
4. 決断の提案で全選択肢が解決可能な場合、採用後に `inspect()` が通ること（`structure` にエラーが増えない）
